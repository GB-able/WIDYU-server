# ADR-0021: 이슈·브랜치 없는 코드 수정을 PreToolUse 훅으로 차단한다

> Architecture Decision Record. 하나의 중요한 의사결정과 그 이유를 기록한다.

| 항목 | 값 |
| --- | --- |
| 상태 | Accepted |
| 날짜 | 2026-08-25 |
| 관련 | Issue #524, ADR-0018 |

## 맥락 (Context)

새 세션이 이슈·브랜치를 새로 만들지 않고 현재 체크아웃된 브랜치에 무관한 변경을 얹는 일이
반복됐다. 예를 들어 `feature/510`(복약 인증 중복 차단)에서 작업이 끝난 뒤 다음 세션이 그
브랜치를 그대로 물려받아 다른 작업을 쌓는 식이다.

작업 순서 규칙(`develop` 최신화 → 이슈 생성 → `feature/{번호}` 브랜치)은 지금까지
루트 `CLAUDE.md`와 `.agents/skills/issue/SKILL.md`에 **문장으로만** 있었다.
`CLAUDE.md`는 시스템 프롬프트가 아니라 사용자 메시지처럼 붙는 권유라서, 지켜지지 않을 때
이를 막을 방법이 없다. 규칙을 더 강하게 적으면 준수율은 오르지만 보장은 되지 않는다.

기존 하네스는 `PostToolUse`(`on-file-edit.sh` — 수정 후 Java 규칙 검사)와
`Stop`(`on-stop.sh` — 정적 규칙 → `compileJava` → Codex 시맨틱 검수)을 갖췄으나,
**실행 전에 차단하는 `PreToolUse`가 없었다.** 잘못된 브랜치에 파일이 이미 쓰인 뒤에야
잡히거나, 세션이 끝날 때에야 잡히는 구조다. 브랜치는 사후 검증으로 되돌리기 번거롭다.

### ADR-0018과의 관계

ADR-0018은 `.claude/settings.json`의 `deny` 규칙을 실측해 **"deny는 보안 경계가 아니라
실수 방지용 가드"** 라는 결론을 남겼다. 명령 문자열 파서를 우회하는 방법(`tail`·`sed`·
인터프리터·괄호 서브셸)이 남아 있기 때문이다.

이번 훅도 같은 성격이다. 브랜치 검사는 `Edit`·`Write` 도구 호출만 가로채므로 Bash로
파일을 쓰면 통과한다. 이 결정은 **악의적 우회를 막는 장치가 아니라 사고를 막는 장치**라는
전제 위에 서 있고, 그 전제가 아래 fail-open 선택의 근거가 된다.

## 결정 (Decision)

`PreToolUse(Edit|Write)` 시점에 `scripts/harness/pre-edit-branch-guard.sh`를 두고
두 단계로 차단한다.

1. **`main`·`develop`에서의 코드 수정은 무조건 차단한다.** 해제 수단을 두지 않는다.
2. **그 외 브랜치는 세션당 최초 1회만 차단한다.** 해당 세션이 이 브랜치에서 작업하기로
   확인했다는 ack 파일이 있으면 통과시킨다. ack는 `(세션 × 브랜치)` 단위라 세션 도중
   브랜치를 바꾸면 다시 확인한다.

차단 메시지에는 두 선택지(새 작업이면 `/issue`, 이어서 하는 작업이면 ack 생성)를 함께
안내하고, **사용자에게 묻지 않고 ack를 만들지 말라**고 명시한다.

기존 훅과 동일하게 Silent Success를 따른다. 통과는 무출력 `exit 0`, 차단만 stderr + `exit 2`.

검사 대상에서 제외하는 경로는 `apiDocs/`, `.claude/`, `.agents/`, `*.log`, 저장소 밖 파일이다.

## 고려한 대안 (Considered Options)

1. **CLAUDE.md에 규칙을 더 강하게 적는다** — 비용 0. 그러나 지금까지 이미 적혀 있었고
   지켜지지 않아서 이 ADR이 생겼다. 같은 층위의 처방을 반복하는 것이라 기각.

2. **`SessionStart` 훅으로 현재 브랜치·최근 커밋을 컨텍스트에 주입한다** — 마찰이 없고
   맥락은 깔린다. 그러나 주입된 정보를 보고 판단하는 주체가 여전히 모델이라 권유에 머문다.
   차단이 아니라 안내다. 보조 수단으로는 유효하나 단독으로는 기각.

3. **모든 브랜치에서 매 편집마다 차단하고 매번 확인을 요구한다** — 가장 강하지만 마찰이
   커서 ack를 기계적으로 만들고 넘어가는 우회가 굳어진다. 규칙이 형식화되면 없느니만 못하다. 기각.

4. **`main`·`develop`만 하드 차단하고 feature 브랜치는 세션당 1회 확인** — 채택.
   되돌리기 어려운 쪽(보호 브랜치 오염)은 해제 불가로 막고, 판단이 필요한 쪽(이 feature
   브랜치가 맞는가)은 **세션이 시작될 때 한 번 의식적으로 결정하게** 만든다.
   반복 마찰 없이 "조용한 드리프트"만 끊는 지점이다.

### fail-open vs fail-closed

`pre-bash-guard`(계획 중인 파괴적 명령·시크릿 차단 훅)는 **fail-closed**로,
이 브랜치 가드는 **fail-open**으로 설계했다. JSON 파싱에 실패하면 통과시킨다.

성격이 다르기 때문이다. 시크릿·파괴적 명령은 한 번 새면 되돌릴 수 없으므로 모를 때
막는 쪽이 맞다. 반면 브랜치 가드가 fail-closed면 `python3`가 없거나 stdin이 깨지는
순간 **모든 파일 편집이 전면 중단된다.** 막으려는 사고(잘못된 브랜치 커밋)는
`git switch`로 되돌릴 수 있는데, 대가는 작업 불능이다. 비용이 역전된다.

## 결과 (Consequences)

### 긍정

- 보호 브랜치(`main`·`develop`) 오염이 구조적으로 불가능해진다. 문서 준수에 기대지 않는다.
- 세션이 브랜치를 물려받아 조용히 드리프트하는 경로가 끊긴다. 최초 1회 차단이
  "이 브랜치가 맞나"를 강제로 묻는 지점이 된다.
- 한 번 확인한 뒤에는 무출력이라 반복 마찰이 없다.
- 기존 훅 3종과 같은 규약(Silent Success, `exit 2` + stderr)이라 배우거나 예외를 둘 게 없다.

### 부정 / 트레이드오프

- **Bash로 파일을 쓰면 통과한다.** `Edit`·`Write` 도구만 가로챈다. ADR-0018과 같은 한계이고,
  같은 이유로 이 훅을 보안 경계로 취급하면 안 된다.
- **ack 파일을 만드는 판단 자체는 여전히 모델이 한다.** 메시지로 "사용자에게 묻지 않고
  2번을 고르지 마라"고 지시했지만 이건 다시 권유다. 훅이 보장하는 건 "한 번은 멈춘다"까지다.
- 세션마다 첫 코드 편집에서 한 번 멈추는 마찰이 생긴다. 의도된 비용이다.
- 제외 경로 목록이 하드코딩이라 저장소 구조가 바뀌면 같이 손봐야 한다.

## 후속 / 미결정

- 제외 경로는 `apiDocs/`·`.claude/`·`.agents/`·`*.log`로 시작한다. 실제로 쓰면서 마찰이
  생기는 경로가 나오면 조정한다. 반대로 `docs/`처럼 지금은 대상인 경로가 과하다고 판단되면
  뺀다.
- ack를 파일이 아니라 `Tasks`·세션 상태로 옮길 수 있는지는 확인하지 않았다. 현재는
  `.claude/state/`에 남기는데, 이 디렉터리는 `on-stop.sh`의 Codex 라운드 상태와 같은 자리다.
- `SessionStart` 훅으로 현재 브랜치·직전 커밋·열린 이슈를 미리 깔아 두면 차단 빈도 자체가
  줄어들 수 있다. 대안 2를 보조 수단으로 다시 볼 여지가 있다.
- 팀에 배포한 뒤 다른 사람 세션에서 마찰이 어느 정도인지 확인한다. 과하면 `main`·`develop`
  하드 차단만 남기고 2단계를 빼는 것도 선택지다.
