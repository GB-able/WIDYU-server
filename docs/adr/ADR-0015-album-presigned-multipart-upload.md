# ADR-0015: 앨범 미디어 Presigned Multipart 직접 업로드

> Architecture Decision Record. 하나의 중요한 의사결정과 그 이유를 기록한다.

| 항목 | 값 |
| --- | --- |
| 상태 | Accepted |
| 날짜 | 2026-07-27 |
| 관련 | ADR-0004, LLD-0021, #450 |

## 맥락 (Context)

ADR-0004는 서버 경유 S3 업로드를 채택하고 영상 처리를 `@Async` 파이프라인으로 분리했다.
그러나 앨범 영상은 최대 2GB까지 허용되며, 실측 기준 279MB 영상이 클라이언트 → API 서버 → S3로 두 번 네트워크를 통과한다.
이 구조는 다음 문제를 남긴다.

- 대용량 파일 수신 동안 요청 스레드와 EC2 인바운드 대역폭을 점유한다.
- 모바일 네트워크에서 업로드가 중단되면 전체 파일을 처음부터 다시 전송해야 한다.
- 업로드 수신량이 늘어날수록 API 서버 자체가 병목이 된다.

AWS는 100MB 이상 파일에 Multipart Upload를 권장하며, 파트 병렬 업로드와 실패 파트 단위 재시도를 지원한다.

## 결정 (Decision)

**앨범 미디어 업로드 경로에 한해 Presigned URL 기반 S3 직접 업로드**로 전환한다.
CPU 집약적인 영상 처리(FFmpeg 압축·썸네일)는 기존 `@Async` 파이프라인을 그대로 재사용한다.

- 서버가 업로드 세션을 발급한다: object key 생성(회원별 스테이징 prefix), 이미지는 presigned PUT URL, 영상은 `CreateMultipartUpload` 후 파트별 presigned URL
- 클라이언트가 S3에 직접 업로드하고 파트별 ETag를 수집한다
- 완료 API에서 서버가 `CompleteMultipartUpload`를 실행하고 `HeadObject`로 크기·Content-Type을 검증한 뒤 앨범을 저장한다
- 영상은 스테이징 원본을 임시 파일로 내려받아 기존 `AlbumVideoProcessingService` 파이프라인으로 처리한다
- 업로드 세션은 Redis `@RedisHash` + `@TimeToLive`로 관리하고, 완료 세션은 짧은 TTL로 남겨 완료 API를 멱등 처리한다
- S3 이벤트(Lambda·SQS) 기반 완료 감지는 도입하지 않는다 — 이벤트는 최소 한 번 전달·순서 미보장이므로 현 단계에서는 클라이언트 완료 API가 더 단순하다
- 기존 서버 경유 API(`POST /api/v1/albums/upload`)는 유지한다 (클라이언트 마이그레이션 기간)

### 보안·무결성 원칙

- object key는 서버가 생성하며 클라이언트는 지정할 수 없다 (`albums/staging/{memberId}/{sessionId}/...`)
- presigned URL 만료는 짧게 유지한다 (1시간)
- 이미지 presigned PUT은 Content-Type·Content-Length를 서명에 포함해 선언과 다른 파일을 차단한다
- 완료 시 `HeadObject`로 실제 크기·타입이 선언 메타데이터와 일치하는지 검증한다

## 고려한 대안 (Considered Options)

1. **서버 경유 업로드 유지 (ADR-0004 현행)** — 검증·압축을 서버에서 일괄 처리
   - 장점: 구조 단순, 클라이언트 변경 없음
   - 단점: 대용량 파일이 서버를 두 번 통과, 업로드 중단 시 전체 재전송, 서버 대역폭 병목
2. **Presigned Multipart 직접 업로드 + 완료 API (채택)** — 업로드 수신과 미디어 처리를 분리
   - 장점: 대용량 데이터가 API 서버를 통과하지 않음, 파트 단위 재시도·병렬 업로드, 발급 응답이 즉시 반환
   - 단점: 미완료 업로드·방치 스테이징 객체 정리 정책 필요, 클라이언트 업로드 로직 복잡도 증가
3. **S3 Event + Lambda/SQS 기반 완료 감지** — 업로드 완료를 서버가 이벤트로 수신
   - 장점: 클라이언트 완료 호출 불필요, 워커 확장 용이
   - 단점: 이벤트 중복·역순 처리 필요, 별도 인프라 운영 부담. 현 팀 규모에서 과다
   - **채택하지 않음**: 트래픽 증가로 `@Async` 처리가 한계에 도달할 때 SQS 워커 전환과 함께 재검토

## 결과 (Consequences)

### 긍정
- 대용량 미디어가 API 서버를 통과하지 않아 요청 스레드·인바운드 대역폭을 절약한다
- 실패한 파트만 재전송할 수 있어 모바일 네트워크 업로드 안정성이 개선된다
- 업로드 진행률·중단 재개를 클라이언트에서 구현할 수 있다
- 영상 처리 파이프라인·실패 보상(ADR-0010)·알림 격리(ADR-0011)를 그대로 재사용한다

### 부정 / 트레이드오프
- 전체 영상 처리 시간은 줄지 않는다 — 서버가 S3에서 원본을 다시 내려받아 FFmpeg 처리하므로 CPU·디스크 비용은 남는다
- 미완료 multipart 파트에는 저장 비용이 계속 발생한다 → S3 Lifecycle 규칙으로 자동 중단·삭제 필요 (버킷 설정 작업)
- 서버가 파일 수신 시점에 내용을 검증할 수 없다 → 완료 시 HEAD 검증으로 대체, 콘텐츠 스캔은 범위 밖

## 후속 / 미결정
- 기존 서버 경유 API 폐기 시점 — 클라이언트 전환 완료 후 별도 결정
- 트래픽 증가 시 `@Async` 처리를 SQS 워커로 교체하는 시점
- S3 Lifecycle 규칙 적용 (미완료 multipart 1일 후 중단, `albums/staging/` 7일 후 만료) — 운영 버킷 설정 작업
