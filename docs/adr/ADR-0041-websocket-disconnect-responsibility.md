# ADR-0041: WebSocket 끊김 대응을 서버·앱 책임으로 나눈다

> Architecture Decision Record. 하나의 중요한 의사결정과 그 이유를 기록한다.

| 항목 | 값 |
| --- | --- |
| 상태 | Proposed |
| 날짜 | 2026-11-04 (2026-11-05 시니어 앱 동작 확인 결과 반영) |
| 관련 | #953, #969(결정 2 구현), LLD-0041(센서 배치, REST 재전송), LLD-0047(심박 배치), LLD-0048(위치 원본), LLD-0049(기기 하트비트), LLD-0088(일회용 토큰, 세션 ACK), LLD-0091(느린 경로 격리, `TEMPORARILY_BUSY`), LLD-0114(재연결 몰림), LLD-0121(실시간 위치 부수효과를 커밋 뒤로), ADR-0017, ADR-0030, ADR-0031, ADR-0039 |

## 맥락 (Context)

시니어 폰 앱은 워치와 폰의 데이터(위치, 심박, IMU)를 모아 서버로 보낸다. 서버로 보내는 통로는 폰 하나이고, 주 통로는 STOMP WebSocket(`/ws/location`)이다. 보호자 앱은 같은 WebSocket으로 시니어의 위치와 심박 방송을 구독한다.

끊김 대응은 장애가 날 때마다 서버 쪽에서 개별 LLD로 쌓였다. 서버와 앱이 각자 무엇을 보장하는지 정한 문서가 없었고, 시니어 앱이 실제로 어떻게 동작하는지는 2026-11-05 앱 팀의 동작 정리(시니어 앱 develop `17cd0a1`, 1.0.0+1 기준)로 처음 확인했다. 확인된 문제는 아래와 같다.

1. **위치만 유실 대비가 없다.** 앱의 위치와 센서 처리는 다음처럼 다르다.

   | 항목 | 위치 | 심박, IMU 배치 |
   | --- | --- | --- |
   | 큐에서 지우는 때 | STOMP `send()`가 예외 없이 끝나면 큐에 넣지도 않는다. 서버 수신 확인이 아니다 | `/user/queue/sensor/result` 결과나 REST 응답을 받은 뒤 |
   | 저장 위치 | 백그라운드 isolate 메모리만. 서비스가 재시작되면 사라진다 | 메모리와 워치 Data Layer(디스크). 앱이 죽어도 다시 읽는다 |
   | 상한 | 720건. 넘치면 가장 오래된 것을 버린다 | 응답 대기, 재전송 큐 각 2,520건. 워치 쪽 IMU 30분분, 심박 720묶음 |
   | 끊겼을 때 | 재연결 뒤 WebSocket으로 한 루프에서 속도 제한 없이 전부 보낸다 | REST(`POST /api/v1/sensor/batches`)로 같은 `batch_id`를 보낸다 |
   | 서버 응답 | 위치 ACK(`/user/queue/location/ack`)를 구독하지 않는다 | 결과 값과 무관하게 최종 판정으로 보고 지운다 |

2. **소켓이 조용히 끊기면 앱이 늦게 안다.** 서버 CONNECTED의 heart-beat는 `10000,10000`이고 앱은 라이브러리 기본값으로 이를 따른다. 그래서 TCP가 정상 종료되지 않은 끊김은 20~30초 뒤에야 감지한다. 그 사이 `send()`는 성공하므로 그 동안의 위치는 서버에 오지 않았는데도 큐에 남지 않는다.

3. **위치 ACK로는 저장 여부를 알 수 없다.** 위치 원본 저장(`LocationFixService.store`)이 실패해도 서버는 WARN만 남기고 ACK를 보낸다(`RealtimeLocationService.storeQuietly`). ACK 본문(`LocationUpdateResponse`)에는 요청 식별자(`seq`)도 없다. 앱은 밀린 위치를 한꺼번에 보내고 서버는 같은 세션의 메시지를 inbound 실행기에서 동시에 처리하므로, ACK가 보낸 순서대로 온다고 가정할 수도 없다.

4. **재연결은 앱 혼자 하지만 몰림을 막는 장치가 없다.** 앱은 재연결 간격을 5초에서 시작해 두 배씩 늘리고 60초에서 멈춘다. 지터와 CONNECT 제한 시간은 없다. 서버 재배포로 모든 시니어 앱이 함께 끊기면 5초 뒤 거의 동시에 붙고, 서버가 소켓만 받고 CONNECTED를 주지 않으면 소켓이 닫힐 때까지 기다린다.

5. **보호자 쪽 누락 방송은 다시 오지 않는다.** Simple Broker는 메모리 기반이라 보호자가 끊긴 동안 나간 위치와 심박 방송을 재전송하지 않는다(`architecture/websocket.md`). 보호자 앱(WIDYU-care)이 재연결 뒤 무엇을 하는지는 확인하지 않았다.

6. **시니어 기기가 오래 끊겨도 아무도 모른다.** LLD-0049의 기기 하트비트(`POST /api/v1/device/heartbeats`, `socket_connected`, `queue_depth`)는 앱에 구현되지 않았고 개발 서버 `device_heartbeat`는 0행이다. release 빌드에는 앱 로그도 원격 로그도 없어 서버 기록이 유일한 운영 근거다.

그 밖의 앱 사실: Android 포그라운드 서비스 하나가 연결, 위치 수집, 전송을 맡아 백그라운드와 화면 꺼짐에서도 계속 돈다. 배터리 최적화 예외는 요청하지 않는다. iOS 백그라운드 전송은 없다. 심박 단건 전송(`/app/heart-rate/send-single`)은 앱에서 제거됐다(앱 #113). 위치는 Android `intervalDuration` 5초, `distanceFilter` 1m 스트림에 값이 올 때마다 `move`로, 60초 동안 보낸 것이 없으면 `keepalive`로 보낸다.

### 관찰된 사례 (개발 서버, 출처는 각 항목)

- **재연결 몰림:** 2026-10-29 10:52, 12:45 회원 30의 폰이 1~2시간 통신하지 못하다 재연결하며 20초 안에 위치 45건, 84건을 보냈고 커넥션 풀이 고갈됐다(LLD-0114 §1). 같은 날 19:45, LLD-0114 배포(16:09) 뒤에는 53분 치 위치 720건이 6초 안에 들어왔고 커넥션 획득 실패와 원본 저장 실패가 0건이었다(2026-10-30 개발 서버 `location_fix`, API 로그 재집계, LLD-0114에는 미기록). 이 속도는 속도 제한 없이 큐를 한 번에 비우는 앱 동작과 맞는다.
- **위치 큐 상한 초과로 버려짐:** 위의 19:45 재전송은 정확히 720건(seq 2016~2735)이었고, 같은 세션의 직전 위치는 18:15의 seq 1902였다. 그 사이 seq 1903~2015(113건)는 서버에 오지 않았다. 2026-10-31 회원 29도 같은 세션에서 seq 6639~6840(202건)이 빠진 채 722건(720건과 새 위치 2건)이 재전송됐다. 이동 중에는 위치가 4~5초마다 생겨 720건이 약 1시간 분량이다(앱 문서의 "keepalive 기준 12시간"은 정지 상태 기준이다). (2026-11-05 개발 서버 `location_fix` 조회)
- **세션 안 빠진 위치:** 2026-10-22 이후 같은 `(device_id, session_id)` 안에서 빠진 `seq`는 회원 29가 487건, 회원 30이 667건, 회원 28이 8건이다. 10건 넘게 한꺼번에 빠진 구멍의 합은 682건으로 큐 상한 초과와 맞는다. 10건 이하 구멍의 합 480건은 끊김 감지 전 유실인지 LLD-0114 배포 전 원본 저장 실패인지 데이터만으로 구분할 수 없다. (2026-11-05 개발 서버 `location_fix` 조회)
- **REST 재전송 복구:** 2026-10-29 19:24 회원 29의 IMU 배치 1건이 WebSocket 경로에서 S3 5초 제한을 넘겨 `FILE_UPLOAD_FAILED`였고, 52초 뒤 같은 `batch_id`가 REST로 와서 `STORED`됐다(개발 서버 API 로그, `sensor_batch`). 앱이 결과를 기다리다 시간 초과 후 REST 큐로 넘기는 설계대로의 동작이다.

### 이미 있는 서버 대응 (확인된 사실)

| 단계 | 현재 동작 | 근거 |
| --- | --- | --- |
| 끊김 감지 | STOMP heartbeat 10초/10초. 종료 코드와 사유를 로그에 남기고 세션 등록을 지운다 | `WebSocketConfig`, `WebSocketEventListener`, `WebSocketSessionRegistry` |
| 재연결 인증 | 30초 일회용 토큰(`POST /api/v1/ws/token`)으로만 handshake. 재연결마다 새 토큰 | LLD-0088, `WsTokenService` |
| 중복 저장 방지 | **저장 단계**의 멱등 키: 센서 `batch_id`, 심박 `(member_id, measured_at)`, 위치 `(device_id, session_id, seq)` | LLD-0041, 0047, 0048 |
| 대체 경로 | 센서와 심박 배치는 REST로도 받는다 | LLD-0041 §3.1 |
| 재연결 몰림 | 위치 1건이 커넥션 1개만 쓴다. v2 위치(`ts_ms` 있음)는 15분 안에 잰 것이면서 현재 최신보다 나중에 잰 것만 실시간에 반영하고, 그 밖은 원본만 저장한다 | LLD-0114 |
| 과부하 | 심박, 센서 전용 실행기가 차면 실행하지 않고 `/user/queue/errors`에 `TEMPORARILY_BUSY` | LLD-0091 |

**중복 방지는 저장에만 해당한다.** 위치 한 건은 검증 → 실시간 반영 판정(DB 트랜잭션) → 커밋 뒤 Redis 최신값 저장과 방송(LLD-0121) → 원본 저장 순서로 처리되고, 멱등 검사는 마지막 원본 저장에서 한다. 같은 위치가 다시 오면 저장은 한 번이지만, Redis 최신값이 만료됐거나 다른 세션의 요청이 겹치면 실시간 방송과 안전구역 판정이 다시 돌 수 있다.

## 결정 (Decision)

원칙: **앱은 서버가 "더 보낼 필요 없다"고 답하기 전까지 보낼 데이터를 지우지 않는다. 서버는 같은 데이터가 여러 번 와도 한 번만 저장한다.** 실시간 방송의 중복은 최신 시각 비교로 줄이되 완전히 막지는 않는다.

1. **재연결은 앱 책임이다.** 끊기면 지수 백오프로 재연결한다. 순서는 ① `POST /api/v1/ws/token`으로 새 WS 토큰(30초 일회용, 401이면 액세스 토큰 리프레시 후 재요청) ② CONNECT ③ 기존 구독 전부 다시 맺기다. 서버 재배포도 같은 절차로 복구한다. 앱은 이미 이 순서로 동작한다(5초부터 두 배, 최대 60초). 여기에 **무작위 지연(지터)과 CONNECT 제한 시간**을 더한다. 서버 설정은 바꾸지 않는다.

2. **위치 ACK를 "더 보낼 필요 없음" 신호로 바꾼다 (서버 변경, #969).**
   - ACK 본문에 요청의 `deviceId`, `sessionId`, `seq`와 처리 결과 `result`를 더한다. 기존 필드는 그대로 둔다. 보호자 방송과 REST 조회 응답은 바꾸지 않는다.
   - `result`는 셋이다. `STORED`(원본을 저장함), `DUPLICATE`(이미 저장된 위치), `REJECTED`(검증 실패, 다시 보내도 같다). 앱은 셋 모두 큐에서 지운다. 센서 결과를 다루는 앱 코드와 같은 방식이다.
   - **원본 저장이 실패하면 ACK를 보내지 않는다.** 실시간 반영이 이미 끝났더라도 원본이 없으면 앱이 다시 보내게 한다. 따로 오류 형식을 정하지 않는다. 앱은 ACK가 제한 시간 안에 오지 않거나 연결이 끊기면 다시 보낸다.
   - 식별자를 읽을 수 있는 v2 위치가 검증에 실패하면 `REJECTED` ACK를 보낸다. ACK를 받아야 지우는 방식에서 검증 실패에 아무 응답도 하지 않으면 앱이 그 위치를 끝없이 다시 보내기 때문이다. 본문을 읽지 못해 식별자가 없으면 지금처럼 `/user/queue/errors`로 간다.
   - 다시 보낸 위치의 원본은 멱등 키로 한 번만 저장된다. 실시간 경로는 Redis 최신 위치가 남아 있으면 LLD-0114 조건으로 걸러지지만, 그 사이 최신값이 만료됐으면 같은 위치가 다시 방송될 수 있다.
   - 원본 조건(`v=2`, `device_id`, `ts_ms`, `LocationUpdateRequest.isRawFix`)을 갖추지 않은 **구형 위치**는 원본을 저장하지 않는다. 구형 위치의 ACK는 새 필드가 null이고 "실시간 처리 완료"만 뜻한다. 현재 시니어 앱은 v2만 보낸다.

3. **WebSocket 오류 본문 형식은 지금 바꾸지 않는다 (보류).**
   - 발신 세션 `/user/queue/errors`의 본문은 `{"error", "message"}`뿐이라 `ErrorCode.code`와 요청 식별자가 없다(`WebSocketExceptionHandler.handle`, `WebSocketWorkDispatcher.OVERLOADED`). 처음 초안은 여기에 `code`, `retryable`, 요청 식별자를 더하려 했다.
   - 앱은 `/user/queue/errors`를 로그로만 남기고 처리하지 않으며, 두 경로 모두 오류 형식 없이 복구된다. 위치는 결정 2에 따라 ACK가 오지 않으면 다시 보낸다. 센서는 결과가 시간 안에 오지 않으면(앱 기준 10~40초, 다른 결과는 오는데 이 배치만 안 오면 2분~2분 30초) REST로 다시 보낸다. 과부하(`TEMPORARILY_BUSY`)와 S3 실패(`FILE_UPLOAD_FAILED`)는 `/user/queue/errors`로 가므로 이 시간 초과 경로로 복구된다.
   - 앱이 오류 본문을 읽어 판단해야 하는 경우가 생기면 그때 형식을 정한다.
   - 앱이 큐를 다루는 기준은 아래와 같다.

   | 응답 | 뜻 | 앱 동작 |
   | --- | --- | --- |
   | 위치 ACK `result` `STORED`, `DUPLICATE` (결정 2 이후), 센서 결과 `STORED`, `DUPLICATE` | 저장됨 | 큐에서 삭제 |
   | 위치 ACK `result` `REJECTED` (결정 2 이후), 센서 결과 `REJECTED`, REST 400, 409, 422 | 검증 실패, 다시 보내도 같다 | 큐에서 삭제하고 로그 |
   | REST 401, 403, 그 밖의 4xx, 5xx, 네트워크 오류 | 일시 실패로 본다 | 큐에 남기고 다시 보낸다 |
   | 응답 없음(제한 시간 초과, 연결 끊김), `/user/queue/errors` | 처리 여부 모름 | 큐에 남기고 다시 보낸다(서버가 저장 멱등으로 흡수) |

   - **결정 2 배포 전까지(과도기):** 위치 ACK에 식별자가 없어 앱은 지금처럼 `send()` 성공 시 지운다. 끊김 감지 전 유실과 원본 저장 실패분 유실 위험은 현재 상태와 같다.

4. **센서와 심박 배치는 WebSocket이 끊겨 있거나 결과가 늦으면 REST로 보낸다.** 이미 있는 경로이고 앱도 이 방식으로 동작한다. 이를 계약으로 확정한다. 재연결을 기다리지 않아도 원본이 저장되고, REST 응답의 `result`, `code`로 결정 3의 표를 따른다. 심박 단건 경로는 앱에서 제거됐으므로 끊긴 동안의 심박 보존은 배치 v2(`stream: "hr"`)가 맡는다(ADR-0031).

5. **위치는 새 REST 경로 없이 WebSocket으로 재전송하되, 재연결 직후 가장 최근 위치 하나를 먼저 보내고 그 ACK를 받은 뒤 나머지를 보낸다.** 나머지 밀린 위치는 한꺼번에 보내도 된다.
   - 이유: 서버의 최신값 비교는 원자적이지 않다(LLD-0114 한계). 가장 최근 위치와 15분 이내의 밀린 위치가 동시에 처리되면 둘 다 옛 최신값과 비교해 통과하고, 밀린 위치가 나중에 쓰이면 옛 위치가 최신값으로 남아 방송된다. 가장 최근 위치의 ACK를 받은 뒤에는 서버 최신값이 그 위치이므로 밀린 위치는 몇 건이 동시에 와도 "최신보다 먼저 잰 위치"로 걸러져 원본만 저장된다.
   - 서버는 `seq` 순서에 의존하지 않는다. 원본 멱등은 `(device_id, session_id, seq)` 존재 여부로만 판단한다(`LocationFixService.store`). 재전송 중 새로 잰 위치가 섞여 도착해도 된다.
   - 한꺼번에 보내도 되는 근거는 1회 관찰이다. LLD-0114 배포 뒤 720건을 6초에 받으면서 커넥션 실패가 없었다(관찰 사례). 여러 기기가 동시에 재연결하는 경우는 측정하지 않았다.
   - **이 효과는 v2 위치이고 가장 최근 위치가 15분 안에 잰 것일 때만 성립한다.** 가장 최근 위치도 15분이 지났으면 실시간 반영이 없고, 보호자 화면은 마지막으로 반영된 위치에 머물다 다음 새 측정이 들어올 때 갱신된다.
   - `ts_ms`가 없는 구형 위치는 시각 비교 없이 매번 반영된다. 구형 앱은 재전송 순서에 따라 과거 위치가 방송될 수 있다.
   - 같은 회원의 다른 세션이 겹치면 최신값 비교가 원자적이지 않다는 LLD-0114의 한계는 그대로다.

6. **보호자 쪽은 재전송하지 않고 재조회한다.** 서버는 누락 방송을 보관하거나 재전송하지 않는다. 보호자 앱은 재연결과 재구독 직후 대상 시니어 ID를 넣어 REST로 다시 읽는다.
   - 마지막 위치 `GET /api/v1/location/realtime/senior/{seniorId}`, 이동 경로 `GET /api/v1/location/realtime/senior/{seniorId}/trail`
   - 심박 상태 `GET /api/v1/heart-rate/status?memberId={seniorId}`, 최근 위급 여부 `GET /api/v1/heart-rate/emergency/recent?memberId={seniorId}` (`memberId`를 빼면 호출자 자신을 조회한다)
   - **재조회 응답과 새 방송이 엇갈릴 때:** 실시간 방송은 서버가 이미 최신 여부를 판정한 값이다(LLD-0114 반영 조건, 구형 위치는 판정 없이 반영). 그래서 앱은 **방송을 받으면 항상 덮어쓰고** REST 응답을 먼저 적용한다. 방송이 REST보다 먼저 만들어졌는데 늦게 도착하면 화면이 한 단계 옛 위치로 돌아갈 수 있고, 다음 방송이 오면 회복된다. 위치 방송 간격은 이동 중 대부분 5~15초, 정지 중 `keepalive` 약 60초다(앱 설정 `intervalDuration` 5초, `distanceFilter` 1m, 2026-11-03~05 개발 서버 `location_fix` 간격).
   - 위치 응답의 `updatedAt`은 측정 시각이 아니라 응답을 만든 시각(`LocationUpdateResponse.of`의 `now()`)이라 비교 기준이 될 수 없다. 위치 방송과 조회 응답에 서버의 최신 비교 기준(`measuredAtMs = min(ts_ms, 처리 시각)`, LLD-0114 §5)을 싣는 방안은 **보호자 앱 동작을 확인한 뒤로 보류**한다. 심박은 `measuredAt`이 측정 시각이므로 REST 응답의 `measuredAt`이 더 늦을 때만 적용한다.
   - 보호자 앱이 실제로 재조회하는지와 위 규칙을 따르는지는 확인하지 않았다(후속 2).
   - 위급 알림은 WebSocket이 아니라 FCM Outbox로 **전송**된다(`HeartRateEmergencyNotificationService`, `IncidentEscalation`). 따라서 WebSocket 끊김은 위급 알림 전송 경로에 영향이 없다. 보호자 기기의 FCM 수신 자체는 이 ADR 범위 밖이다.

7. **시니어 기기의 장기 단절은 서버가 감지해 알린다 (서버 신규, 별도 LLD, 후속).**
   - **하트비트에 기대지 않는다.** 처음 초안은 실시간 통로 단절을 하트비트의 `socket_connected=false`로 판정하려 했지만 앱에 하트비트가 없다. 서버는 단일 인스턴스이고 WebSocket 연결과 종료 이벤트를 이미 받는다(`WebSocketEventListener`, `WebSocketSessionRegistry`). 회원별로 연결된 세션이 있는지를 서버가 직접 판정한다. 앱 작업이 필요 없고 앱이 보고하는 값보다 정확하다.
   - **수신 기록을 따로 둔다.** 저장된 행의 `server_received_at_ms`로는 판정할 수 없다. 중복 재전송(`DUPLICATE`)은 새 행을 만들지 않고 구형 위치는 `location_fix`에 저장되지 않기 때문이다. 그래서 서버는 **저장 여부와 무관하게** 회원별 마지막 데이터 수신 시각 `last_data_rx`를 기록한다(예: Redis 키). 위치(구형 포함), 센서와 심박 배치(REST, WebSocket, 결과 무관) 중 무엇이든 서버에 도착하면 갱신한다. 위치 `keepalive`(60초)가 생존 신호 역할을 하고, 위치 서비스가 꺼지면 위치만 멈추므로 심박과 IMU 수신도 함께 본다.
   - 시각은 서버 수신 시각만 쓴다. 앱이 늦게 재전송한 옛 데이터의 측정 시각(`ts_ms`)으로 판정하면 끊긴 기간이 정상으로 보인다.
   - **두 상태를 따로 판정하고 따로 해제한다.**

     | 상태 | 판정 | 해제 |
     | --- | --- | --- |
     | 데이터 단절 | `last_data_rx`가 기준 시간(미정)보다 오래됨. 앱이 서버에 아무것도 못 보내는 상태 | 어떤 데이터든 새로 도착(`last_data_rx` 갱신). 재전송된 옛 데이터도 포함 |
     | 실시간 통로 단절 | 데이터 단절은 아니지만 그 회원의 WebSocket 세션이 기준 시간 동안 하나도 없음. REST는 살아 있지만 위치의 유일한 통로가 끊긴 상태 | 그 회원의 WebSocket 세션이 다시 연결됨 |

   - 알림은 상태 진입당 한 번 보낸다. 받는 사람과 기준 시간은 미결정(후속 1)이다.

## 고려한 대안 (Considered Options)

1. **외부 브로커(RabbitMQ STOMP relay 등)로 메시지 보관과 재전송** — 보호자 누락 방송을 재전송할 수 있지만, 위치와 심박은 최신값만 의미가 있어 REST 재조회로 충분하다. 단일 서버에 브로커 운영 부담만 늘어난다. 기각.
2. **서버 메모리에 보호자별 누락 메시지 버퍼** — 서버 재시작과 배포로 사라지고, 다중 서버로 가면 다시 설계해야 한다. 기각.
3. **위치 REST 배치 API 추가** — 몰림 자체를 줄이지만 크기 제한, 부분 실패, 배치 ACK 계약이 새로 필요하다. LLD-0114 배포 뒤 개발 서버에서 720건/6초 몰림을 커넥션 실패 없이 처리했다(1회 관찰, 위 사례). 결정 5로 몰림이 다시 문제가 되면 도입한다. 보류.
4. **위치 ACK 의미를 바꾸지 않고 원본 유실을 감수 (B안)** — 서버 변경이 없지만, 앱이 `send()` 성공이나 ACK로 큐를 지우는 순간 끊김 감지 전 유실과 원본 저장 실패분은 복구할 수 없다. 원본은 연구 실증 자료라 유실을 감수할 수 없다. 기각.
5. **WebSocket 끊김(`SessionDisconnectEvent`) 즉시 알림** — 망 전환 같은 짧은 끊김은 앱 재연결로 복구된다. 결정 7은 기준 시간 동안 이어진 단절만 알린다. 기각.
6. **SockJS 폴백(HTTP 스트리밍, 롱 폴링)에 끊김 대응 맡기기** — `/ws/location`에 `withSockJS()`가 켜져 있지만, 앱은 SockJS URL 형식만 쓰고 websocket 트랜스포트만 사용한다(대체 트랜스포트 없음). 폴백 전송도 세션이 끊기면 미전달 메시지를 재전송하지 않는다. 데이터 보존은 앱 큐와 REST 대체 경로로 맡긴다. 기각.
7. **위치 원본 저장 실패를 재시도 가능한 오류 본문으로 알림 (초안의 결정 2, 3)** — 앱이 `/user/queue/errors`를 처리하지 않아 오류 형식을 만들어도 읽는 쪽이 없다. ACK를 보내지 않는 것만으로 앱의 시간 초과 재전송이 같은 결과를 낸다. 기각.

## 결과 (Consequences)

- 지금 하는 서버 변경은 결정 2(#969)다. 위치 ACK에 `deviceId`, `sessionId`, `seq`, `result`를 싣고, 원본 저장 실패 시 ACK를 보내지 않고, 검증 실패한 v2 위치에 `REJECTED` ACK를 보낸다.
- 워치 큐가 넘쳐 버린 IMU 구간 기록(`stream: "imu_dropped"`)을 서버가 받아 저장한다(앱 페이로드 형식 대기). 지금은 허용 stream(`hr`, `imu_watch`, `imu_phone`) 밖이라 `SENSOR_BATCH_INVALID`로 거절되고, 앱은 `send()` 성공 시 지워 전부 사라진다. 결측 구간마다 사유를 저장하라는 정책(데이터정책서 B 1.2.4, 1.2.6, 값 목록은 합의 대기 S2)의 근거 자료다.
- 결정 3(오류 본문 형식)과 결정 6의 위치 비교 시각 필드는 보류다. 결정 7(장기 단절 알림)은 기준 시간과 받는 사람이 정해진 뒤 별도 LLD로 만든다.
- 앱에 요청하는 순서는 아래와 같다.
  1. 위치 큐 상한 상향. 이동 중에는 720건이 약 1시간 분량이라 큰 구멍의 직접 원인이다. 상수 하나만 바꾸면 된다.
  2. 위치 ACK 구독과 ACK 기반 삭제, 재연결 직후 가장 최근 위치 우선(결정 2 배포 뒤). 끊김 감지 전 유실과 원본 저장 실패분을 막는다.
  3. 위치 큐 디스크 저장(앱에 sqflite가 이미 있다). 서비스 재시작과 앱 종료 때 유실을 막는다. ACK 없이 디스크만 쓰면 죽은 소켓에 쓴 위치는 여전히 사라지므로 2와 함께 한다.
  4. 재연결 지터와 CONNECT 제한 시간. 지금 데이터를 잃는 원인은 아니지만 사용자가 늘면 재배포 때 동시 재연결이 몰린다.
  5. 배터리 최적화 예외 요청. 제조사 절전 정책이 서비스를 멈출 수 있지만 장기 공백과의 관련은 확인하지 못했다. Google Play 정책상 사용 가능한지 먼저 확인한다.
- 데이터 유실 방지는 앱 큐에 달려 있다. 앱이 위 1~3을 구현하지 않으면 서버가 버텨도 끊긴 동안의 위치는 사라진다.
- 구형 위치는 끊긴 동안의 보존을 보장하지 않는다. 보존은 v2 위치와 배치 v2 심박이 맡는다.
- 보호자 화면은 재연결 직후 REST 재조회를 거쳐야 최신 상태가 된다. 그 사이 몇 초는 이전 화면이 보일 수 있다.
- 장기 단절은 기준 시간이 지나서야 알 수 있다. 짧을수록 빨리 알지만 오탐이 늘어난다.
- `architecture/websocket.md`에 결정 3의 응답 표와 결정 6의 재조회 목록을 옮겨 적는다.

## 후속 / 미결정

1. 장기 단절 알림의 기준 시간과 받는 사람(보호자, 운영자, 둘 다), 실증 참가자와 일반 사용자를 다르게 할지.
2. 앱 팀 확인: 시니어 앱은 2026-11-05 동작 정리(앱 develop `17cd0a1`)로 확인했다. 보호자 앱(WIDYU-care)의 재연결 뒤 REST 재조회와 방송 처리 규칙은 미확인이다. 앱이 결정 1~5를 구현하면 그 버전을 이 ADR에 기록한다.
3. `imu_dropped` 페이로드 형식(구간 시작과 끝, 버린 개수, 식별자 유무)과 저장 위치는 앱 형식을 받은 뒤 LLD에서 정한다.
4. 전송 경로와 유실 관측: 센서 배치가 WebSocket과 REST 중 어디로 들어왔는지 DB에 남기지 않는다(스레드 이름으로만 구분). 결정 7의 수신 기록 지점에 경로 태그 카운터를 두면 REST 비중을 볼 수 있다. 위치는 같은 세션 안에서 빠진 `seq` 수를 유실 지표로 둔다. 서버 데이터만으로 유실량을 잴 수 있고, 앱의 큐 상한 상향과 ACK 기반 삭제의 효과를 이 값으로 확인한다.
5. 다중 서버 확장 시 브로커 중계와 세션 재검증, 결정 7의 회원별 세션 판정, 같은 회원의 여러 세션에서 최신값 비교를 원자적으로 만드는 방법은 이 ADR 범위 밖이다.
