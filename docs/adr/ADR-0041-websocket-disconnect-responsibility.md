# ADR-0041: WebSocket 끊김 대응을 서버·앱 책임으로 나눈다

> Architecture Decision Record. 하나의 중요한 의사결정과 그 이유를 기록한다.

| 항목 | 값 |
| --- | --- |
| 상태 | Proposed |
| 날짜 | 2026-11-02 |
| 관련 | #953, LLD-0041(센서 배치·REST 재전송), LLD-0049(기기 하트비트), LLD-0088(일회용 토큰·세션 ACK), LLD-0091(느린 경로 격리·`TEMPORARILY_BUSY`), LLD-0114(재연결 몰림), ADR-0017, ADR-0030, ADR-0039 |

## 맥락 (Context)

시니어 폰 앱은 워치와 폰의 데이터(위치·심박·IMU)를 모아 서버로 보낸다. 서버로 보내는 통로는 폰 하나이고, 주 통로는 STOMP WebSocket(`/ws/location`)이다. 보호자 앱은 같은 WebSocket으로 시니어의 위치·심박 방송을 구독한다.

끊김 대응은 장애가 날 때마다 서버 쪽에서 개별 LLD로 쌓였다. 서버와 앱이 각자 무엇을 보장하는지 정한 문서가 없어, 아래가 비어 있다.

1. **앱 동작이 확인되지 않았다.** 재연결 간격, `TEMPORARILY_BUSY`를 받은 뒤 재전송 여부(LLD-0091 §8), 재연결 뒤 ACK를 받고 다음 위치를 보내는지(LLD-0114 범위 밖, FE 요청만 함)를 모른다. 앱이 재전송하지 않으면 거절된 데이터는 저장되지 않는다.
2. **위치에는 REST 대체 경로가 없다.** 센서·심박 배치는 REST(`POST /api/v1/sensor/batches`)로도 받지만 위치는 WebSocket(`/app/location/update`)으로만 받는다. 끊긴 동안 쌓인 위치가 재연결 순간 WebSocket으로 몰린다. 2026-10-29 19:45 회원 30의 폰은 53분 치 위치 720건을 6초 안에 보냈다(LLD-0114 배포 후라 커넥션 실패 0).
3. **보호자 쪽 누락 방송은 다시 오지 않는다.** Simple Broker는 메모리 기반이라 보호자가 끊긴 동안 나간 위치·심박 방송을 재전송하지 않는다(`architecture/websocket.md`). 재연결 뒤 무엇을 다시 조회해야 하는지 앱 계약이 없다.
4. **시니어 기기가 오래 끊겨도 아무도 모른다.** 폰이 60초마다 REST로 보내는 하트비트(`socket_connected`, `queue_depth`)는 쌓이지만 끊김 알림은 LLD-0049 범위 밖이었다. 2026-10-29 회원 30의 폰은 1~2시간 서버와 통신하지 못했고, 그동안 위급 판정도 보호자 알림도 불가능했다.

### 이미 있는 서버 대응 (확인된 사실)

| 단계 | 현재 동작 | 근거 |
| --- | --- | --- |
| 끊김 감지 | STOMP heartbeat 10초/10초. 종료 코드·사유를 로그에 남기고 세션 등록을 지운다 | `WebSocketConfig`, `WebSocketEventListener` |
| 재연결 인증 | 30초 일회용 토큰(`POST /api/v1/ws/token`)으로만 handshake. 재연결마다 새 토큰 | LLD-0088 |
| 중복 재전송 | 멱등 키로 무해하게 처리: 센서 `batch_id`, 심박 `(member_id, measured_at)`, 위치 `(device_id, session_id, seq)` | LLD-0041·0047·0048 |
| 대체 경로 | 센서·심박 배치는 REST로도 받는다. 10/29 S3 타임아웃 배치가 REST 재전송으로 저장된 사례가 있다 | LLD-0041 §3.1 |
| 재연결 몰림 | 위치 1건이 커넥션 1개만 쓰고, 15분이 지났거나 최신보다 먼저 잰 위치는 원본만 저장하고 방송하지 않는다 | LLD-0114 |
| 과부하 | 심박·센서 전용 실행기가 차면 실행하지 않고 `/user/queue/errors`에 `TEMPORARILY_BUSY` | LLD-0091 |

## 결정 (Decision)

원칙은 하나다. **앱은 서버 ACK를 받기 전까지 보낼 데이터를 지우지 않고, 서버는 같은 데이터가 여러 번 와도 한 번만 반영한다.** 이 위에서 단계별 책임을 아래처럼 나눈다.

1. **재연결은 앱 책임이다.** 앱은 끊기면 지수 백오프(예: 1초부터 두 배씩, 최대 30초, 무작위 지연 포함)로 재연결한다. 매번 새 WS 토큰을 받고, CONNECT 뒤 기존 구독을 모두 다시 맺는다. 서버 설정은 바꾸지 않는다.

2. **끊긴 동안의 시니어 데이터는 앱 큐가 보관한다.** 앱은 위치·센서·심박을 폰 큐에 두고 해당 ACK를 받은 것만 지운다. ACK가 없거나 `TEMPORARILY_BUSY`·오류를 받으면 큐에 남기고 백오프 후 다시 보낸다. 서버는 기존 멱등 키로 중복을 흡수한다. 이 동작은 앱 팀 확인 전까지 **가정**이다.

3. **센서·심박 배치는 WebSocket이 끊겨 있으면 REST로 보낸다.** 이미 있는 경로를 계약으로 확정한다. 재연결을 기다리지 않아도 원본이 저장된다.

4. **위치는 새 REST 경로 없이 WebSocket으로 재전송하되, 재연결 직후 가장 최근 위치를 먼저 보낸다.** 그 뒤 밀린 위치를 오래된 순으로, 이전 ACK를 받은 다음 하나씩 보낸다.
   - 최신 위치가 먼저 실시간에 반영되므로, 뒤이어 오는 밀린 위치는 LLD-0114 조건(최신보다 먼저 잰 위치)에 따라 원본만 저장되고 방송되지 않는다. 보호자 화면이 과거 위치로 빨리 감기 되지 않는다.
   - ACK 순서 전송이면 기기당 동시 처리가 하나라, LLD-0114가 남긴 "최신 위치 비교가 원자적이지 않다"는 한계도 실제로는 생기지 않는다.

5. **보호자 쪽은 재전송하지 않고 재조회한다.** 서버는 누락 방송을 보관·재전송하지 않는다. 보호자 앱은 재연결·재구독 직후 REST로 현재 상태를 다시 읽는다.
   - 마지막 위치 `GET /api/v1/location/realtime/senior/{memberId}`
   - 이동 경로 `GET /api/v1/location/realtime/senior/{memberId}/trail`
   - 심박 상태 `GET /api/v1/heart-rate/status?memberId=`, 최근 위급 여부 `GET /api/v1/heart-rate/emergency/recent`
   - 위급 알림 자체는 WebSocket이 아니라 FCM(Outbox)으로 가므로 WebSocket 끊김과 무관하다.

6. **시니어 기기의 장기 단절은 서버가 감지해 알린다.** 기준 신호는 WebSocket 연결이 아니라 **하트비트 수신**이다. 하트비트는 REST라 WebSocket 상태와 독립적이고, 앱이 살아 있는지를 직접 보여 준다. 마지막 하트비트가 기준 시간(미정)보다 오래되면 한 번 알리고, 다시 들어오면 해제한다. 받는 사람과 기준 시간은 미결정(후속 1)이다. 구현은 별도 LLD로 한다.

## 고려한 대안 (Considered Options)

1. **외부 브로커(RabbitMQ STOMP relay 등)로 메시지 보관·재전송** — 보호자 누락 방송을 재전송할 수 있지만, 위치·심박은 최신값만 의미가 있어 REST 재조회로 충분하다. 단일 서버에 브로커 운영 부담만 늘어난다. 기각.
2. **서버 메모리에 보호자별 누락 메시지 버퍼** — 서버 재시작이나 배포로 사라지고, 다중 서버로 가면 다시 설계해야 한다. 기각.
3. **위치 REST 배치 API 추가** — 몰림 자체를 줄이지만 크기 제한·부분 실패·배치 ACK 계약이 새로 필요하다. LLD-0114 뒤 720건/6초 몰림을 실패 없이 처리했으므로 지금은 필요하지 않다. 결정 4로 몰림이 다시 문제가 되면 도입한다. 보류.
4. **WebSocket 끊김(`SessionDisconnectEvent`) 즉시 알림** — 망 전환·백그라운드 전환 같은 짧은 끊김은 앱 재연결로 복구되므로 알릴 대상이 아니다. 또 WebSocket만 끊기고 REST 재전송은 되는 상태를 장애로 오인한다. 하트비트 무수신이 "앱이 서버에 아무것도 못 보낸다"를 더 정확히 나타낸다. 기각.
5. **SockJS·롱 폴링 대체 전송** — 네이티브 앱 클라이언트라 브라우저 호환용 대체 전송이 필요 없고, 데이터 대체 경로는 이미 REST로 있다. 기각.

## 결과 (Consequences)

- 서버 변경은 결정 6(장기 단절 알림) 하나다. 나머지는 이미 있는 동작을 계약으로 확정하는 것이다.
- 데이터 유실 방지는 앱 큐에 달려 있다. 앱이 결정 1·2·4를 구현하지 않으면 서버가 아무리 버텨도 끊긴 동안의 데이터는 사라진다. 앱 팀 확인이 이 ADR의 전제다.
- 보호자 화면은 재연결 직후 한 번 REST 재조회를 거쳐야 최신 상태가 된다. 그 사이 몇 초는 이전 화면이 보일 수 있다.
- 하트비트 기준이라, 앱이 강제 종료되거나 폰이 꺼지면 기준 시간이 지나서야 알 수 있다. 기준 시간이 짧을수록 빨리 알지만 오탐이 늘어난다.
- `architecture/websocket.md`에 이 책임 표를 옮겨 적는다.

## 후속 / 미결정

1. 장기 단절 알림의 기준 시간과 받는 사람(보호자·운영자·둘 다), 실증 참가자와 일반 사용자를 다르게 할지.
2. 앱 팀 확인: 재연결 백오프, ACK 전 큐 보관, `TEMPORARILY_BUSY`·오류 수신 후 재전송, 재연결 직후 최신 위치 우선 전송, 보호자 재연결 후 REST 재조회. 현재 구현과 다르면 차이를 이 ADR에 기록한다.
3. 전송 경로 관측: 센서 배치가 WebSocket과 REST 중 어디로 들어왔는지 DB에 남기지 않는다(스레드 이름으로만 구분). 결정 3의 REST 비중을 보려면 경로 태그가 붙은 수신 카운터를 추가한다.
4. 다중 서버 확장 시 브로커 중계와 세션 재검증은 이 ADR 범위 밖이다.
