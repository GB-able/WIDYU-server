# ADR-0041: WebSocket 끊김 대응을 서버·앱 책임으로 나눈다

> Architecture Decision Record. 하나의 중요한 의사결정과 그 이유를 기록한다.

| 항목 | 값 |
| --- | --- |
| 상태 | Proposed |
| 날짜 | 2026-11-04 |
| 관련 | #953, LLD-0041(센서 배치·REST 재전송), LLD-0047(심박 배치), LLD-0048(위치 원본), LLD-0049(기기 하트비트), LLD-0088(일회용 토큰·세션 ACK), LLD-0091(느린 경로 격리·`TEMPORARILY_BUSY`), LLD-0114(재연결 몰림), ADR-0017, ADR-0030, ADR-0039 |

## 맥락 (Context)

시니어 폰 앱은 워치와 폰의 데이터(위치·심박·IMU)를 모아 서버로 보낸다. 서버로 보내는 통로는 폰 하나이고, 주 통로는 STOMP WebSocket(`/ws/location`)이다. 보호자 앱은 같은 WebSocket으로 시니어의 위치·심박 방송을 구독한다.

끊김 대응은 장애가 날 때마다 서버 쪽에서 개별 LLD로 쌓였다. 서버와 앱이 각자 무엇을 보장하는지 정한 문서가 없어, 아래가 비어 있다.

1. **앱 동작이 확인되지 않았다.** 재연결 간격, `TEMPORARILY_BUSY`를 받은 뒤 재전송 여부(LLD-0091 §8), 재연결 뒤 ACK를 받고 다음 위치를 보내는지(LLD-0114 범위 밖, FE 요청만 함)를 모른다.
2. **위치 ACK로는 저장 여부를 알 수 없다.** 위치 원본 저장(`LocationFixService.store`)이 실패해도 서버는 WARN만 남기고 ACK를 보낸다(`RealtimeLocationService.storeQuietly`, LLD-0114 §5-6). ACK 본문(`LocationUpdateResponse`)에는 요청 식별자(`seq`)도 없어, 앱이 어느 큐 항목의 ACK인지 맞출 수 없다.
3. **위치에는 REST 대체 경로가 없다.** 센서·심박 배치는 REST(`POST /api/v1/sensor/batches`)로도 받지만 위치는 WebSocket(`/app/location/update`)으로만 받는다. 끊긴 동안 쌓인 위치가 재연결 순간 WebSocket으로 몰린다.
4. **보호자 쪽 누락 방송은 다시 오지 않는다.** Simple Broker는 메모리 기반이라 보호자가 끊긴 동안 나간 위치·심박 방송을 재전송하지 않는다(`architecture/websocket.md`). 재연결 뒤 무엇을 다시 조회해야 하는지 앱 계약이 없다.
5. **시니어 기기가 오래 끊겨도 아무도 모른다.** 폰이 60초마다 REST로 보내는 하트비트(`socket_connected`, `queue_depth`)는 쌓이지만 끊김 알림은 LLD-0049 범위 밖이었다.

### 관찰된 사례 (개발 서버, 출처는 각 항목)

- **재연결 몰림:** 2026-10-29 10:52·12:45 회원 30의 폰이 1~2시간 통신하지 못하다 재연결하며 20초 안에 위치 45건·84건을 보냈고 커넥션 풀이 고갈됐다(LLD-0114 §1). 같은 날 19:45, LLD-0114 배포(16:09) 뒤에는 53분 치 위치 720건이 6초 안에 들어왔고 커넥션 획득 실패·원본 저장 실패가 0건이었다(2026-10-30 개발 서버 `location_fix`·API 로그 재집계, LLD-0114에는 미기록).
- **REST 재전송 복구:** 2026-10-29 19:24 회원 29의 IMU 배치 1건이 WebSocket 경로에서 S3 5초 제한을 넘겨 `FILE_UPLOAD_FAILED`였고, 52초 뒤 같은 `batch_id`가 REST로 와서 `STORED`됐다(개발 서버 API 로그·`sensor_batch`, LLD 미기록).

### 이미 있는 서버 대응 (확인된 사실)

| 단계 | 현재 동작 | 근거 |
| --- | --- | --- |
| 끊김 감지 | STOMP heartbeat 10초/10초. 종료 코드·사유를 로그에 남기고 세션 등록을 지운다 | `WebSocketConfig`, `WebSocketEventListener` |
| 재연결 인증 | 30초 일회용 토큰(`POST /api/v1/ws/token`)으로만 handshake. 재연결마다 새 토큰 | LLD-0088, `WsTokenService` |
| 중복 저장 방지 | **저장 단계**의 멱등 키: 센서 `batch_id`, 심박 `(member_id, measured_at)`, 위치 `(device_id, session_id, seq)` | LLD-0041·0047·0048 |
| 대체 경로 | 센서·심박 배치는 REST로도 받는다 | LLD-0041 §3.1 |

**중복 방지는 저장에만 해당한다.** 위치는 실시간 갱신·방송을 먼저 하고 멱등 검사는 그 뒤 원본 저장에서 한다. 같은 위치가 다시 오면 저장은 한 번이지만, Redis 최신값이 만료됐거나 다른 세션의 요청이 겹치면 실시간 방송·안전구역 판정이 다시 돌 수 있다.

## 결정 (Decision)

원칙: **앱은 서버가 "저장했다"고 답하기 전까지 보낼 데이터를 지우지 않는다. 서버는 같은 데이터가 여러 번 와도 한 번만 저장한다.** 실시간 방송의 중복은 최신 시각 비교로 줄이되 완전히 막지는 않는다.

1. **재연결은 앱 책임이다.** 끊기면 지수 백오프(예: 1초부터 두 배씩, 최대 30초, 무작위 지연 포함)로 재연결한다. 순서는 ① 액세스 토큰이 만료됐으면 리프레시 ② `POST /api/v1/ws/token`으로 새 WS 토큰(30초 일회용, 만료·사용 실패 시 다시 발급) ③ CONNECT ④ 기존 구독 전부 다시 맺기다. 서버 재배포도 같은 절차로 복구한다. 서버 설정은 바꾸지 않는다.

2. **위치 ACK를 "저장 완료" 신호로 바꾼다 (서버 변경, 후속 이슈).**
   - ACK 본문에 요청의 `device_id`·`session_id`·`seq`를 그대로 담는다. 앱은 이 셋으로 큐 항목을 찾아 지운다.
   - 원본 저장이 실패하면 ACK를 보내지 않고 결정 3의 오류 형식으로 재시도 가능한 오류를 보낸다. 실시간 반영은 이미 끝났더라도 원본이 없으면 앱이 다시 보내게 한다.
   - 다시 보낸 위치의 원본은 멱등 키로 한 번만 저장된다. 실시간 경로는 Redis 최신 위치가 남아 있으면 LLD-0114 조건으로 걸러지지만, 그 사이 최신값이 만료됐으면 같은 위치가 다시 방송될 수 있다.
   - 원본 조건(`v=2`·`device_id`·`ts_ms`, `LocationUpdateRequest.isRawFix`)을 갖추지 않은 **구형 위치**는 원본을 저장하지 않는다. 구형 위치의 ACK는 계속 "실시간 처리 완료"만 뜻하므로, 구형 앱의 위치는 큐 보관·재전송 대상이 아니다(최선 노력). 원본 보존이 필요하면 앱이 v2로 보내야 한다.

3. **WebSocket 오류 응답에 판단 근거를 싣고(서버 변경, 후속 이슈), 앱은 재시도할 응답과 최종 응답을 나눈다.**
   - **현재 형식의 한계:** 발신 세션 `/user/queue/errors`의 본문은 `{"error", "message"}`뿐이다. 과부하는 `error: "TEMPORARILY_BUSY"`로 오지만, 업무 예외는 `error: "BusinessException"`처럼 예외 클래스 이름만 오고 `FILE_5000`·`LOCATION_4000` 같은 `ErrorCode.code`와 요청 식별자가 없다(`WebSocketExceptionHandler.handle`, `WebSocketWorkDispatcher.OVERLOADED`). 센서 `REJECTED` ACK도 거절 사유를 담지 않는다. REST 오류는 응답 본문의 `code`로 판단할 수 있다.
   - **바꿀 형식:** WebSocket 오류 본문에 `code`(`ErrorCode.code`), `retryable`(true/false), 요청 식별자(센서 `batch_id`·`seq`, 위치 `device_id`·`session_id`·`seq`)를 추가한다. 기존 `error`·`message`는 유지한다.
   - 앱은 아래 표대로 큐를 다룬다.

   | 응답 | 뜻 | 앱 동작 |
   | --- | --- | --- |
   | v2 위치 ACK(결정 2 이후), 센서·심박 배치 `STORED`·`DUPLICATE` | 저장됨 | 큐에서 삭제 |
   | 센서 `REJECTED`, `retryable=false` 오류(`SENSOR_4000`~`4003`, `SENSOR_4090`, `LOCATION_4000`, `AUTH_4030` 등) | 검증 실패, 다시 보내도 같다 | 큐에서 삭제하고 로그 |
   | `retryable=true` 오류(`SRV_5031`, `FILE_5000`, 결정 2의 위치 저장 실패, 그 밖의 5xx) | 서버 쪽 일시 실패 | 큐에 남기고 백오프 후 재전송 |
   | 응답 없음(제한 시간 초과·연결 끊김) | 처리 여부 모름 | 큐에 남기고 재전송(서버가 저장 멱등으로 흡수) |

   - **형식 변경 전까지(과도기):** `error`가 `TEMPORARILY_BUSY`이거나 응답이 없으면 재시도한다. 그 밖의 `/user/queue/errors`는 일시 실패인지 최종 거절인지 구분할 수 없다. 이런 항목은 **지우지 않고** 같은 항목을 정해진 횟수(예: 3회)까지 다시 보낸 뒤 폰의 **보류 큐**로 옮긴다. 보류 큐는 일반 전송을 막지 않고, 재연결할 때나 일정 간격(예: 1시간)으로 다시 시도한다. 결정 3의 형식이 배포되면 `retryable=false` 응답을 받은 항목만 지운다. 저장되지 않은 자료를 앱이 판단만으로 지우지 않기 위해서다.
   - 요청 식별자를 얻지 못한 오류(본문을 읽지 못함, 과부하 거절처럼 식별자가 없는 응답)는 어느 항목에 대한 것인지 알 수 없으므로 "응답 없음"과 같이 다룬다. 식별자를 싣는 방법은 후속 LLD에서 정한다.

4. **센서·심박 배치는 WebSocket이 끊겨 있으면 REST로 보낸다.** 이미 있는 경로를 계약으로 확정한다. 재연결을 기다리지 않아도 원본이 저장되고, REST 응답의 `result`·`code`로 결정 3을 판단한다.
   - 심박 **단건**(`/app/heart-rate/send-single`, ACK `/user/queue/heart-rate/result`)은 저장 확인 신호가 아니다. 응답(`HeartRateStatusResponse`)에 요청 식별자가 없고, DB 접근이 실패해도 AI 판정만으로 응답한다(`HeartRateService`의 DB 실패 분기). 단건 경로는 배치 v2 전환 전까지 남겨 둔 경로(ADR-0031)이므로 **큐 보관 대상에서 뺀다**. 끊긴 동안의 심박 보존은 배치 v2(`stream: "hr"`)가 맡는다.

5. **위치는 새 REST 경로 없이 WebSocket으로 재전송하되, 재연결 직후 가장 최근 위치를 먼저 보낸다.** 그 뒤 밀린 위치를 오래된 순으로, 이전 ACK를 받은 다음 하나씩 보낸다.
   - **이 효과는 v2 위치이고 최신 위치가 15분 안에 잰 것일 때만 성립한다.** 그때 최신 위치가 먼저 실시간에 반영되고, 뒤이어 오는 밀린 위치는 "최신보다 먼저 잰 위치"라 원본만 저장되고 방송되지 않는다.
   - 최신 위치도 15분이 지났으면(앱이 15분 넘게 아무 위치도 못 쟀으면) 실시간 반영이 없다. 보호자 화면은 마지막으로 반영된 위치에 머물고, 다음 새 측정이 들어올 때 갱신된다.
   - `ts_ms`가 없는 구형 위치는 시각 비교 없이 매번 반영된다. 구형 앱은 재전송 순서에 따라 과거 위치가 방송될 수 있다.
   - ACK 순서 전송은 **한 기기 세션 안의** 동시 처리를 하나로 줄일 뿐이다. 같은 회원의 다른 세션이 겹치면 최신값 비교가 원자적이지 않다는 LLD-0114의 한계는 그대로다.

6. **보호자 쪽은 재전송하지 않고 재조회한다.** 서버는 누락 방송을 보관·재전송하지 않는다. 보호자 앱은 재연결·재구독 직후 대상 시니어 ID를 넣어 REST로 다시 읽는다.
   - 마지막 위치 `GET /api/v1/location/realtime/senior/{seniorId}`, 이동 경로 `GET /api/v1/location/realtime/senior/{seniorId}/trail`
   - 심박 상태 `GET /api/v1/heart-rate/status?memberId={seniorId}`, 최근 위급 여부 `GET /api/v1/heart-rate/emergency/recent?memberId={seniorId}` (`memberId`를 빼면 호출자 자신을 조회한다)
   - **재조회 응답과 새 방송이 엇갈릴 때:** 실시간 방송은 서버가 이미 최신 여부를 판정한 값이다(LLD-0114 반영 조건, 구형 위치는 판정 없이 반영). 그래서 앱은 **방송을 받으면 항상 덮어쓰고**, 시각 비교는 REST 재조회 응답을 화면에 적용할지 정할 때만 쓴다.
   - 위치 응답의 `updatedAt`은 측정 시각이 아니라 응답을 만든 시각(`LocationUpdateResponse.of`의 `now()`)이라 비교 기준이 될 수 없다. 그래서 **위치 방송·조회 응답에 비교 시각 필드를 추가한다**(서버 변경, 결정 2·3과 같은 후속 이슈). 이 값은 원래 `ts_ms`가 아니라 **서버가 최신 비교에 쓰는 정규화 값**이다. 서버는 최신 위치의 비교 기준을 `measuredAtMs = min(ts_ms, 처리 시각)`으로 저장하므로(LLD-0114 §5), 같은 잘린 값을 실어야 앱의 비교가 서버 판정과 어긋나지 않는다. 구형 위치와 체류 정보(`StayInfo`)로 대신 답한 REST 응답처럼 비교 시각이 없으면 null로 둔다.
   - 앱은 REST 위치 응답의 비교 시각이 현재 표시값의 비교 시각보다 늦을 때만 적용한다. 어느 한쪽이라도 비교 시각이 없으면, 화면이 비어 있을 때만 REST 응답을 적용한다.
   - **보장 범위:** 화면 순서는 비교 시각이 있는 v2 위치끼리만 보장한다. 늦게 도착한 구형 위치 방송이 더 최신 REST 결과를 덮어쓰는 경우, 그리고 Redis 최신 위치가 만료돼 시각 없는 체류 정보로 답한 REST 결과가 이전 표시값에 밀리는 경우는 최선 노력이다. 두 경우 모두 시니어 앱이 v2 위치를 보내기 시작하면(다음 측정) 회복된다. 시니어 기기가 그대로 오프라인이면 화면은 마지막 위치에 머물고, 이 상태는 결정 7의 장기 단절 알림이 알린다. 심박은 `measuredAt`이 측정 시각이므로 REST 응답의 `measuredAt`이 더 늦을 때만 적용한다.
   - 비교 시각 필드가 배포되기 전까지는 REST 응답을 먼저 적용하고 이후 방송으로 덮어쓴다. 방송이 REST보다 먼저 만들어졌는데 늦게 도착하면 화면이 한 단계 옛 위치로 돌아갈 수 있고, 다음 방송(이동 중 약 5초, 정지 중 약 60초 간격)이 오면 회복된다.
   - 위급 알림은 WebSocket이 아니라 FCM Outbox로 **전송**된다(`HeartRateEmergencyNotificationService`, `IncidentEscalation`). 따라서 WebSocket 끊김은 위급 알림 전송 경로에 영향이 없다. 보호자 기기의 FCM 수신 자체는 이 ADR 범위 밖이다.

7. **시니어 기기의 장기 단절은 서버가 감지해 알린다 (서버 신규, 별도 LLD).**
   - **수신 기록을 따로 둔다.** 저장된 행의 `server_received_at_ms`로는 판정할 수 없다. 중복 재전송(`DUPLICATE`)은 새 행을 만들지 않고, 구형 위치는 `location_fix`에 저장되지 않으며, 하트비트 중복도 행을 만들지 않기 때문이다. 그래서 서버는 **저장 여부와 무관하게** 회원별로 마지막 수신 시각 두 개를 기록한다(예: Redis 키).
     - `last_data_rx`: 그 회원의 위치(구형 포함)·센서 배치(REST·WebSocket, 결과 무관)·심박 단건·하트비트 중 무엇이든 서버에 도착한 시각
     - `last_ws_rx`: WebSocket으로 위치·센서·심박 메시지가 도착한 시각
   - 시각은 서버 수신 시각만 쓴다. 앱이 늦게 재전송한 옛 데이터의 측정 시각(`ts_ms`)으로 판정하면 끊긴 기간이 정상으로 보인다.
   - **두 상태를 따로 판정하고 따로 해제한다.**

     | 상태 | 판정 | 해제 |
     | --- | --- | --- |
     | 데이터 단절 | `last_data_rx`가 기준 시간(미정)보다 오래됨. 앱이 서버에 아무것도 못 보내는 상태 | 어떤 데이터든 새로 도착(`last_data_rx` 갱신). 재전송된 옛 데이터도 포함 |
     | 실시간 통로 단절 | 데이터 단절은 아니지만 `last_ws_rx`가 기준 시간보다 오래되고, 마지막 하트비트의 `socket_connected=false`. REST는 살아 있지만 위치의 유일한 통로가 끊긴 상태 | WebSocket 수신(`last_ws_rx` 갱신) 또는 `socket_connected=true` 하트비트 도착 |

     `socket_connected=false` 하트비트가 다시 도착하면 데이터 단절은 해제되고 실시간 통로 단절은 유지된다.
   - 알림은 상태 진입당 한 번 보낸다. 받는 사람과 기준 시간은 미결정(후속 1)이다.

## 고려한 대안 (Considered Options)

1. **외부 브로커(RabbitMQ STOMP relay 등)로 메시지 보관·재전송** — 보호자 누락 방송을 재전송할 수 있지만, 위치·심박은 최신값만 의미가 있어 REST 재조회로 충분하다. 단일 서버에 브로커 운영 부담만 늘어난다. 기각.
2. **서버 메모리에 보호자별 누락 메시지 버퍼** — 서버 재시작·배포로 사라지고, 다중 서버로 가면 다시 설계해야 한다. 기각.
3. **위치 REST 배치 API 추가** — 몰림 자체를 줄이지만 크기 제한·부분 실패·배치 ACK 계약이 새로 필요하다. LLD-0114 배포 뒤 개발 서버에서 720건/6초 몰림을 커넥션 실패 없이 처리했다(1회 관찰, 위 사례). 결정 5로 몰림이 다시 문제가 되면 도입한다. 보류.
4. **위치 ACK 의미를 바꾸지 않고 원본 유실을 감수 (B안)** — 서버 변경이 없지만, 앱이 ACK를 받고 큐를 지우는 순간 원본 저장 실패분은 복구할 수 없다. 원본은 연구 실증 자료라 유실을 감수할 수 없다. 기각.
5. **WebSocket 끊김(`SessionDisconnectEvent`) 즉시 알림** — 망 전환·백그라운드 전환 같은 짧은 끊김은 앱 재연결로 복구된다. 결정 7은 기준 시간 동안 이어진 단절만 알린다. 기각.
6. **SockJS 폴백(HTTP 스트리밍·롱 폴링)에 끊김 대응 맡기기** — `/ws/location`에 `withSockJS()`가 이미 켜져 있지만, 폴백 전송도 세션이 끊기면 미전달 메시지를 재전송하지 않는다. 앱이 폴백을 쓰는지는 확인하지 않았다(후속 2). 데이터 보존은 폴백이 아니라 앱 큐와 REST 대체 경로로 맡긴다. 기각.

## 결과 (Consequences)

- 서버 변경은 넷이다. 결정 2(위치 ACK에 식별자, 저장 실패 시 재시도 오류), 결정 3(WebSocket 오류 본문에 `code`·`retryable`·요청 식별자), 결정 6(위치 응답에 비교 시각), 결정 7(회원별 수신 시각 기록과 장기 단절 알림). 결정 2·3·6은 같은 응답 계약이라 한 이슈로 묶을 수 있다. 나머지는 이미 있는 동작을 계약으로 확정하는 것이다.
- 결정 2·3 배포 전까지 위치 ACK는 "실시간 처리 완료"만 뜻하고, 오류는 `TEMPORARILY_BUSY` 외에는 구분되지 않는다. 앱은 과도기 규칙(결정 3의 보류 큐, 결정 6의 방송 덮어쓰기)을 따른다. 위치 원본 저장 실패분을 잃을 수 있는 위험은 현재 상태와 같다.
- 보류 큐는 폰 저장 공간을 쓴다. 최종 거절 항목이 형식 변경 전까지 쌓일 수 있으므로, 보관 상한과 넘쳤을 때의 처리는 앱 쪽에서 정한다(후속 2).
- 구형 위치와 심박 단건은 끊긴 동안의 보존을 보장하지 않는다. 보존은 v2 위치와 배치 v2 심박이 맡는다.
- 데이터 유실 방지는 앱 큐에 달려 있다. 앱이 결정 1·3·4·5를 구현하지 않으면 서버가 버텨도 끊긴 동안의 데이터는 사라진다. 앱 팀 확인이 이 ADR의 전제다.
- 보호자 화면은 재연결 직후 REST 재조회를 거쳐야 최신 상태가 된다. 그 사이 몇 초는 이전 화면이 보일 수 있다.
- 장기 단절은 기준 시간이 지나서야 알 수 있다. 짧을수록 빨리 알지만 오탐이 늘어난다.
- `architecture/websocket.md`에 결정 3의 응답 표와 결정 6의 재조회 목록을 옮겨 적는다.

## 후속 / 미결정

1. 장기 단절 알림의 기준 시간과 받는 사람(보호자·운영자·둘 다), 실증 참가자와 일반 사용자를 다르게 할지.
2. 앱 팀 확인: 재연결 백오프와 토큰 재발급 순서, 저장 확인 전 큐 보관, 결정 3의 재시도·최종 구분과 과도기 보류 큐(보관 상한 포함), 재연결 직후 최신 위치 우선 전송, v2 위치·배치 v2 심박 사용 여부, SockJS 폴백 사용 여부, 보호자 재연결 후 REST 재조회와 방송 우선·REST 비교 시각 규칙. 현재 구현과 다르면 차이를 이 ADR에 기록한다.
3. 결정 2·3·6의 오류 코드·필드 이름, 식별자를 얻지 못한 오류의 형식, 위치 비교 시각 필드의 이름과 정규화 규칙은 후속 LLD에서 정한다. 구형 앱 호환(필드 추가만, 기존 필드 유지)을 지킨다.
4. 전송 경로 관측: 센서 배치가 WebSocket과 REST 중 어디로 들어왔는지 DB에 남기지 않는다(스레드 이름으로만 구분). 결정 7의 `last_ws_rx`와 같은 지점에 경로 태그 카운터를 두면 REST 비중을 볼 수 있다.
5. 다중 서버 확장 시 브로커 중계·세션 재검증과, 같은 회원의 여러 세션에서 최신값 비교를 원자적으로 만드는 방법은 이 ADR 범위 밖이다.
