# ADR-0019: 목표 홈 주간 통계 기간 벌크 조회

> Architecture Decision Record. 하나의 중요한 의사결정과 그 이유를 기록한다.

| 항목 | 값 |
| --- | --- |
| 상태 | Accepted |
| 날짜 | 2026-08-20 |
| 관련 | LLD-0024, ADR-0020, #489, #491, #492 |

## 맥락 (Context)

목표 홈의 주간 통계는 날짜별로 복약 스케줄과 걸음 기록을 조회하고, 각 복약 스케줄마다 복약 인증 존재 여부를 다시 조회한다. 보호자 통계는 이번 주 일별 결과를 주간 달성률과 차트 생성 과정에서 중복 계산한다.

2026-08-20 로컬 Before 측정에서 시니어 주간 상태 API는 전체 SQL 21회, 보호자 주간 통계 API는 77회를 실행했다. 보호자 API는 한 요청에서 Buffer Pool 논리 읽기 1,281회를 발생시켰다. 데이터는 Buffer Pool에 적중해 물리 읽기는 발생하지 않았지만, 현재 구조는 날짜 수와 스케줄 수가 늘면 SQL 왕복이 함께 증가한다.

## 결정 (Decision)

주간 통계에 필요한 복약 스케줄·복약 인증·걸음 기록을 조회 기간별로 각각 한 번 조회하고, 날짜별 결과는 애플리케이션 메모리에서 집계한다.

- 기존 `findEffectiveByMemberAndDateRange`, `findByMemberIdAndDateRange`, `findByMemberAndWalkDateBetweenOrderByWalkDateAsc`를 재사용한다.
- 스케줄 버전 유효성은 기존 `MedicineSchedule.isEffectiveOn(date)`로 판정한다.
- 날짜별 복약 인증 스케줄 ID와 걸음 기록을 Map으로 구성해 반복 조회를 제거한다.
- 보호자 통계는 한 번 계산한 이번 주 일별 달성률로 이번 주 전체 달성률도 계산한다.
- 조회 기간은 최대 14일로 제한되어 있으므로 별도 캐시나 집계 테이블을 도입하지 않는다.
- 인덱스는 우선 추가하지 않고 After `EXPLAIN ANALYZE`와 검사 행 수를 보고 별도 판단한다. → 아래 [후속 조치](#후속-조치-2026-08-20-갱신)에서 추가하기로 번복했다.

## 고려한 대안 (Considered Options)

1. **Redis 또는 Spring Cache 적용** — 반복 요청은 줄지만 요청 내부 N+1을 남기고 무효화 정책이 필요해 채택하지 않는다.
2. **DB 집계 쿼리 한 개로 통합** — SQL 왕복은 최소화되지만 복약 스케줄 유효기간과 날짜별 상태 규칙이 복잡한 SQL에 중복되어 채택하지 않는다.
3. **날짜별 DB 조회를 병렬 실행** — 단일 요청 지연을 일부 줄일 수 있지만 SQL 수와 DB 부하는 그대로이며 트랜잭션 컨텍스트를 스레드 간 공유할 수 없어 채택하지 않는다.
4. **기간 벌크 조회 후 메모리 집계** — 기존 Repository와 도메인 규칙을 재사용하고 SQL 수를 고정할 수 있어 채택한다.

## 결과 (Consequences)

### 긍정

- 통계 데이터 SQL이 날짜 수와 스케줄 수에 비례하지 않고 3회로 고정된다.
- 이번 주 일별 결과의 중복 계산이 제거된다.
- 캐시 정합성이나 신규 인프라가 필요 없다.
- 기존 복약 스케줄 버전 유효기간 규칙을 그대로 재사용한다.

After 로컬 측정에서 두 API의 전체 SQL은 4회, 통계 SQL은 3회로 확인됐다. 응답 SHA-256은 Before와 동일했고, Buffer Pool 논리 읽기는 시니어 340→65, 보호자 1,281→78로 감소했다.

### 부정 / 트레이드오프

- 최대 14일치 엔티티를 한 번에 메모리에 적재한다.
- 데이터 규모가 매우 커지면 기간 조회 자체의 검사 행 수와 인덱스를 다시 측정해야 한다.
- Buffer Pool에 적중하는 로컬 측정에서는 물리 디스크 읽기 감소를 직접 확인하지 못할 수 있다.

## 후속 조치 (2026-08-20 갱신)

### 기간 복약 인증 조회에 복합 인덱스를 추가한다 (#492)

당초 이 ADR은 "기간 복약 인증 조회는 현재 23행을 검사해 별도 인덱스를 추가하지 않는다. 운영 데이터에서 병목이 확인되면 복합 인덱스를 별도 이슈로 검토한다"로 결론했다. 이 판단은 **로컬 시드 데이터가 인증 37건뿐이라 병목이 드러나지 않은 상태에서 내린 것**이었고, 재측정 결과 번복한다.

`findByMemberIdAndDateRange`는 `mp.medicineSchedule.member.id`로 필터링해 `medicine_schedule` 조인을 강제했다. 그 결과 옵티마이저가 `medicine_schedule`을 드라이빙 테이블로 잡고 `medicine_schedule_id` FK 인덱스로만 접근하므로, `verified_at`이 인덱스 조건이 아니라 후처리 필터로만 적용된다. **조회 비용이 요청한 날짜 범위가 아니라 해당 시니어의 전체 인증 이력에 비례한다.** 위에서 제거한 N+1이 요청당 SQL *횟수*의 문제였다면, 이쪽은 SQL 한 건의 *비용*이 시간이 갈수록 자라는 문제이므로 방치하면 개선분이 다시 잠식된다.

`MedicationProof`는 이미 자체 `member_id` FK를 보유하므로 조건을 `mp.member.id`로 바꾸고 `(member_id, verified_at)` 복합 인덱스를 추가한다. 두 컬럼의 값은 항상 같다 — `MedicationProofService.verifyMedication`이 저장 전에 `schedule.getMember().getId().equals(currentMember.getId())`를 강제한다.

당초 검토 대상이던 `(member_id, verified_at, medicine_schedule_id)` 대신 두 컬럼만 쓴다. 세 번째 컬럼은 커버링 인덱스를 노린 것인데, 이 조회는 엔티티 전체를 로드하므로 어차피 클러스터드 인덱스를 타야 해 이득이 없고 인덱스만 커진다.

**재측정** — 별도 스키마에 시니어 50명 × 하루 4회 × 730일 = 인증 14.6만 건을 적재했다. 14일 창, 반환 56건 고정, 변형별 50회.

| 변형 | SQL | 인덱스 | 검사 행 | 평균 |
| --- | --- | --- | ---: | ---: |
| A | 조인 (변경 전) | 없음 | 2,924 | 2.773ms |
| B | `mp.member_id` 직접 | 없음 | 2,920 | 2.090ms |
| C | 직접 | `(member_id, verified_at)` | 56 | 0.037ms |
| D | 조인 (변경 전) | `(member_id, verified_at)` | 2,924 | 2.053ms |

**D가 조인 제거와 인덱스 추가를 반드시 함께 해야 하는 이유다.** 조인을 남긴 채 인덱스만 추가하면 옵티마이저가 새 복합 인덱스를 아예 선택하지 않아 검사 행이 A와 동일하다.

같은 14일 창에서 회원 이력만 절반(1,460건)으로 줄이면 A는 1.019ms, B는 1.023ms로 함께 줄지만 C는 0.035ms로 평평하다. 변경 전 비용이 조회 창이 아니라 전체 이력에 비례했다는 뜻이다.

측정 한계 — 합성 데이터라 인증이 매일 정확히 4건씩 균등 분포하며 실제 사용자의 결측·편중을 반영하지 않는다. 순수 SQL 실행 시간이므로 애플리케이션 왕복·직렬화는 포함하지 않았고, k6 API 응답시간 재측정은 하지 않았다.

**트레이드오프** — `medication_proof`에 쓰기 시 인덱스 유지 비용이 추가된다. 복약 인증은 시니어 1명당 하루 수 건 수준의 저빈도 쓰기이므로 읽기 이득이 크게 앞선다.

### 통계 SQL 3회 고정은 영속성 컨텍스트 상태에 의존한다

집계 과정의 `proof.getMedicineSchedule().getId()`는 `MedicineSchedule`이 `@Id`를 필드에 두고 있어 Hibernate의 식별자 단축 경로를 타지 않고 프록시를 초기화한다. 추가 SQL이 발생하지 않는 것은 기간 스케줄 조회가 해당 스케줄을 이미 같은 1차 캐시에 적재해 두었기 때문이다. 기간 조회에 잡히지 않는 스케줄 버전의 인증 기록이 있으면(예: 같은 날 생성·삭제되어 `effectiveTo < effectiveFrom`이 된 버전) 건당 SELECT가 1회씩 추가된다. 집계 결과는 스케줄 목록과 교집합을 취하므로 정확성에는 영향이 없다.

### 인가 검증 누락 (#491)

이 파이프라인을 담은 `GoalHomeController`의 보호자 API 두 개에 가족 접근 검증이 없었다. 별도 결정으로 ADR-0020에 기록한다.
