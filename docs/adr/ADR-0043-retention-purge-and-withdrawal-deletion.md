# ADR-0043: 처리방침 보관 기간의 자동 삭제와 탈퇴 뒤 삭제

> Architecture Decision Record. 하나의 중요한 의사결정과 그 이유를 기록한다.

| 항목 | 값 |
| --- | --- |
| 상태 | Proposed |
| 날짜 | 2026-11-10 |
| 관련 | LLD-0136(보관 기간 정리 작업), LLD-0137(탈퇴와 30일 뒤 삭제), ADR-0036 결정 6을 대체, ADR-0030, ADR-0031, ADR-0034, LLD-0030, LLD-0052, LLD-0059, `docs/operations/study-withdrawal-procedure.md`, #1015(정리 작업 첫 단계: 건수만 세기) |

## 맥락 (Context)

개인정보 처리방침과 위치기반서비스 약관은 자료마다 보관 기간을 약속한다. 서버는 그 기간이 지나도 아무것도 지우지 않는다.

| 자료 | 처리방침 보관 기간 | 서버 자리 |
| --- | --- | --- |
| 심박 측정값 | 30일 | `heart_rate_event`, 심박 묶음의 `sensor_batch` 행과 S3 원문 |
| 움직임 센서 원본 | 30일 | `sensor_batch` 행과 S3 원문, `sensor_dropped_range` |
| 위치 좌표 | 30일. 건강 변화 알림에 붙은 좌표 180일, 안심구역 알림에 붙은 좌표 90일 | `location_fix` |
| 기기 연결 상태 기록 | 90일 | `device_heartbeat` |
| 건강 변화 알림 기록, 알림 응답, 후속 질문 답 | 180일 | `heart_rate_emergency`, `decision_record`, `incident`과 딸린 표, `followup_card`, `followup_answer` |
| 알림센터 항목 | 일반 90일, 건강 변화 알림 180일, 안심구역 알림 90일 | `fcm_notification`(`expires_at` 칸이 있으나 조회에서만 거른다) |
| 앱 알림 발송 대기와 재시도 기록 | 30일 | `fcm_outbox` |
| 위치 열람 기록 | 1년 | `location_access_log` |
| 동의와 철회 기록 | 계정이 있는 동안과 탈퇴 뒤 1년 | `consent_record` |

지금 서버가 지우지 않는 이유는 결정으로 남아 있다.

- ADR-0036 결정 6은 동의 기록, 위치 열람 기록, 관리자 접속기록을 자동 삭제하지 않는다고 정했다. 보관 상한은 법무 검토 뒤로 미뤘다.
- 심박 30일 삭제 스케줄러(`HeartRateCleanupScheduler`)는 정책 근거가 없고 실증 참가자 자료까지 지운다는 이유로 #650에서 제거됐다. 회원 ID 목록으로 실증 참가자를 빼는 스위치(#637, PR #638)는 만들었다가 닫았다.
- ADR-0030은 `sensor_batch`의 정리 기간과 S3 수명주기 정책을 미결정으로 남겼다.

이제 처리방침이 기간을 정했으므로 그 근거가 생겼다. 탈퇴도 처리방침과 다르다. 처리방침은 「탈퇴하면 30일 뒤 지운다, 어르신이 탈퇴하면 위치정보와 위치 열람 기록은 바로 지운다, 어르신도 앱에서 직접 탈퇴할 수 있다」고 약속한다. 지금 보호자 탈퇴는 회원을 비활성으로 바꾸고 이름과 번호를 가릴 뿐 30일 뒤 삭제가 없다. 어르신은 탈퇴할 경로가 없다. 탈퇴 때 실제로 지우는 것은 Redis 실시간 위치(LLD-0059), 복약 인증 사진(LLD-0030), 프로필 사진뿐이다. 앱스토어는 앱 안에서 계정 삭제를 시작할 수 있어야 심사를 통과시키므로 출시 전에 필요하다.

제약은 다음과 같다.

- 실증은 운영 서버에서 진행한다. 실증 참가자 자료는 연구 동의서의 보관 정책(`study_participation`, ADR-0034)을 따르고, 연구 자료 삭제는 수동 절차(`study-withdrawal-procedure.md`)가 맡는다.
- `sensor_batch`는 약 81만 행이고 행마다 S3 객체가 하나다. 인덱스 행이 S3 객체의 유일한 목록이다(ADR-0030 결정 1).
- 회원 행을 FK로 가리키는 테이블이 30개를 넘는다. 결제 기록은 전자상거래법상 5년을 남겨야 한다.
- 배포는 단일 인스턴스다(ADR-0023). 운영 DB는 `ddl-auto: validate`라 새 칸과 테이블은 SQL 스크립트로 먼저 만든다.

## 결정 (Decision)

1. **ADR-0036 결정 6을 대체한다. 처리방침 표의 자료는 서버가 매일 밤 자동으로 지운다.** 대상은 위 표의 테이블과 S3 원문이다. 관리자 접속기록(`admin_access_log`)과 업무 기록(`admin_audit_log`), 결제 기록은 이 결정의 대상이 아니며 지금처럼 자동 삭제하지 않는다. 그 보관 상한은 별도로 정한다.
2. **삭제는 행의 물리 삭제와 S3 객체 삭제다.** 기간이 지난 자료를 익명화해 남기지 않는다. 화면에서 숨기는 것(`expires_at` 조회 조건)은 삭제로 치지 않는다. 예외는 결정 7의 회원 행 하나다.
3. **기간은 서버가 저장한 시각에서 센다.** 기기가 보낸 측정 시각(`measured_at`, `ts_ms`)이 아니라 서버가 행을 만든 시각(`created_at`, 없으면 `accessed_at`, `recorded_at`)을 쓴다. 기기 시계가 틀리거나 늦게 재전송된 자료가 기간보다 일찍 지워지거나 영영 안 지워지는 일을 막는다. 이 시각은 PK와 함께 늘어나므로 새 인덱스 없이 PK 순서로 지울 수 있다.
4. **실증 참가자 자료는 회원 단위로 자동 삭제에서 뺀다.** `study_participation`에 `deletion_processed_at`이 비어 있는 행이 있는 회원은 연구 자료 테이블(센서, 심박, 위치 원본, 기기 상태, 판정, 사건, 후속 질문)의 자동 삭제 대상이 아니다. 알림센터, 발송 대기, 위치 열람 기록, 동의 기록은 연구 자료가 아니므로 참가자도 지운다. 회차 단위가 아니라 회원 단위인 이유는 `heart_rate_emergency`와 단건 경로 `heart_rate_event`에 회차를 가리키는 칸이 없기 때문이다. 연구 자료의 삭제는 지금처럼 수동 절차가 맡는다.
5. **S3 원문은 앱 삭제 작업이 인덱스 행을 따라 지운다. `sensor/` 접두사에 S3 수명주기 만료 규칙을 걸지 않는다.** 작업은 기간이 지난 `sensor_batch` 행을 최대 1,000개 골라 `DeleteObjects`로 원문을 먼저 지우고, 지워진 키의 행만 DB에서 지운다. 실패한 키는 행이 남아 다음 날 다시 대상이 된다. 인덱스 행이 곧 재시도 목록이다. 수명주기 규칙은 버킷 버전 관리가 켜져 있을 때 이전 버전과 삭제 마커를 치우는 용도와, 연구 자료가 없는 임시 접두사에만 쓴다.
6. **백업은 보관 주기가 지나 사라지게 둔다.** 운영 DB에서 지운 자료는 RDS 자동 백업에 보관 기간만큼 남는다. 백업에서 골라 지우지 않는다. 대신 자동 백업 보관 기간을 짧게 정해 처리방침에 적고, 수동 스냅샷은 만들지 않거나 기한을 정해 지운다. 백업으로 복구하면 정리 작업을 곧바로 한 번 돌려 기한이 지난 자료를 다시 지운다.
7. **탈퇴한 회원의 행은 개인정보가 없는 묘비로 남기고, 개인 자료는 탈퇴 30일 뒤 지운다.** `member` 행은 ID, 유형, 상태, 탈퇴 시각, 삭제 완료 시각만 의미를 가진다. 이름과 번호는 지금처럼 탈퇴 즉시 가린다. 결제 기록(5년), 동의 기록(탈퇴 뒤 1년), 관리자 기록(2년)은 회원 ID만으로 남는다. 회원 행을 지우지 않는 이유는 결제 기록이 FK로 회원 행을 가리키고, 30개가 넘는 표를 FK 순서로 지우는 대신 개인 자료 표만 지우면 되기 때문이다.
8. **어르신이 탈퇴하면 그 어르신의 위치 원본(`location_fix`)과 위치 열람 기록(`location_access_log`)을 탈퇴 트랜잭션에서 바로 지운다.** 처리방침의 약속이고, 위치정보법이 동의 철회 때 개인위치정보와 확인자료를 지체 없이 파기하라고 한 조항과 같은 방향이다. 같은 법의 「확인자료 6개월 이상 보존」은 평상시 최소 보존 기간으로 읽고, 탈퇴로 동의가 철회되면 파기 의무가 앞선다고 해석한다. 이 해석은 법무 확인 전이라 이 ADR이 Proposed인 주된 이유다. 실증 참가자도 위치는 즉시 지울지는 결정 필요 사항이다.
9. **처음 켤 때는 지우지 않고 셈만 한다.** 정리 작업과 탈퇴 뒤 삭제 작업은 `enabled`와 `dry-run` 설정을 따로 갖는다. 운영자가 dry-run 건수와 제외 회원 목록을 확인한 뒤에 실제 삭제로 바꾼다. 실행마다 테이블별 지운 건수(dry-run이면 지울 건수)를 DB 표에 남긴다. 정리 작업의 첫 배포(#1015)는 삭제 코드 없이 건수만 세고, `dry-run` 설정은 삭제 경로와 함께 들어온다(LLD-0136 2절).

## 고려한 대안 (Considered Options)

1. **지금처럼 자동 삭제하지 않고 운영자가 주기적으로 SQL로 지운다** — 코드가 필요 없다. 그러나 사람이 매일 지울 수 없고, 처리방침의 기간을 지키지 못하는 날이 생긴다. 지운 기록도 사람마다 다르다. 기각.
2. **S3 수명주기 규칙으로 센서 원문을 30일 뒤 지운다** — 코드 없이 S3가 지운다. 그러나 규칙의 거르기 조건은 접두사와 태그의 「포함」뿐이라 실증 참가자 객체를 뺄 수 없다. 키 `sensor/{memberId}/...`에 날짜도 없다. 업로드 때 태그를 달아도 참가자 등록이 나중에 되면 태그가 틀린다. 또 S3만 지우면 `sensor_batch` 행이 사라진 객체를 가리킨다. 그래도 DB 작업이 필요하므로 얻는 것이 없다. 기각.
3. **삭제 작업 큐(`s3_object_deletion_task`, LLD-0030)에 센서 키를 넣고 기존 재시도 스케줄러가 지우게 한다** — 재시도 구조를 그대로 쓴다. 그러나 기존 스케줄러는 5분에 100건, 하루 약 2만 9천 건이고 객체마다 `DeleteObject`를 한 번 부른다. 81만 행의 첫 정리에 한 달이 걸린다. 날마다 쌓이는 센서 묶음도 겨우 따라간다. 인덱스 행을 남겨 두면 그것이 재시도 목록이 되므로 큐가 필요 없다. 센서에는 기각한다. 탈퇴 회원의 앨범과 프로필처럼 건수가 적은 파일에는 이 큐를 그대로 쓴다.
4. **회원 행까지 지운다** — 회원 ID도 남지 않는다. 그러나 결제, 동의, 관리자 기록이 회원 행을 FK로 가리키고 그 기록은 법정 기간만큼 남겨야 한다. FK를 끊거나 30개가 넘는 표의 삭제 순서를 맞춰야 한다. 묘비 행은 개인정보가 없으므로 남겨도 처리방침과 어긋나지 않는다. 기각.
5. **실증 참가자를 회차(`run_id`) 단위로 뺀다** — 참가자의 회차 밖 일상 자료는 30일 뒤 지워 처리방침에 더 가깝다. 그러나 `heart_rate_emergency`와 단건 심박에는 회차 칸이 없어 표마다 다른 추적이 필요하고, 잘못 추적하면 연구 자료를 되돌릴 수 없게 지운다. 회원 단위로 시작하고 결정 필요 사항으로 남긴다.
6. **기기가 보낸 측정 시각으로 기간을 센다** — 「측정한 날부터 30일」에 더 가깝다. 그러나 기기 시계가 틀리면 결과가 틀리고, 측정 시각 칸은 회원 ID 뒤에만 인덱스가 있어 전체 기간 범위 삭제가 표 전체를 훑는다. 서버 수신 시각과의 차이는 재전송 지연만큼이라 작다. 기각.
7. **백업에서도 탈퇴자와 만료 자료를 골라 지운다** — RDS 자동 백업은 골라 지울 수 없다. 백업을 내려받아 고쳐 다시 올리는 것은 운영 위험이 크다. 기각.

## 결과 (Consequences)

### 긍정
- 처리방침이 약속한 기간을 서버가 매일 집행하고, 날짜와 테이블별 건수가 DB에 남는다.
- 어르신도 앱에서 탈퇴할 수 있고, 탈퇴 뒤 30일이면 개인 자료가 지워진다.
- 실증 참가자 자료는 수동 절차와 연구 보관 정책이 계속 정한다. #650이 걱정한 연구 자료 유실이 생기지 않는다.
- 새 인덱스나 대형 테이블 DDL 없이 PK 순서로 지운다.

### 부정 / 트레이드오프
- 실증 참가자는 연구와 무관한 일상 심박과 위치도 30일보다 오래 남는다. 연구 동의서가 이를 덮는지 확인해야 한다.
- 지운 자료가 백업에 백업 보관 기간만큼 남는다. 처리방침에 이 사실을 적어야 한다.
- 위치 원본을 30일에 지우면 위치 「수집 사실」을 보여 줄 자료도 함께 사라진다. 위치정보법의 확인자료 6개월 보존이 수집 사실에도 적용되면 좌표 없는 수집 기록을 따로 남겨야 한다(결정 필요).
- 탈퇴 즉시 이름과 번호를 가리므로 30일 안에 계정을 되살려도 이름과 번호는 돌아오지 않는다. 30일 복구를 제공하려면 가리는 시점을 30일 뒤로 옮겨야 한다.
- 다른 가족의 알림센터 항목에 남은 탈퇴 어르신의 이름(`senior_display_name`)은 그 항목의 보관 기간까지 남는다.
- 첫 실행 때 밀린 자료가 많다. 하룻밤 상한을 두면 처음 며칠은 기간을 넘긴 자료가 남는다.

## 후속 / 미결정

사용자와 팀이 정해야 할 항목이다. 구현은 이 항목이 정해진 뒤 시작한다.

1. **위치정보법 해석**: 어르신 탈퇴 때 위치 열람 기록을 6개월이 지나기 전이라도 즉시 지우는 것이 맞는가. 위치 원본을 30일에 지울 때 수집 사실 기록을 따로 6개월 이상 남겨야 하는가. 조문 번호(제16조 제2항, 제24조 제4항)도 법무에서 확인한다. 이 문서의 조문 인용은 개발팀이 읽은 것이며 법률 판단이 아니다.
2. **실증 참가자 우선 여부**: 참가자 자료를 회원 단위로 빼는 것에 동의하는가. 참가자가 서비스에서 탈퇴하면 연구 참여 철회로 보는가, 연구 자료만 연구 보관 기간까지 남기는가. 참가자 탈퇴 때 위치는 즉시 지우는가.
3. **위급 알림에 붙은 좌표**: 무엇을 「건강 변화 알림에 붙은 좌표」로 볼 것인가. 서버에서 찾은 후보는 `heart_rate_emergency.location`(단건 경로가 보낸 문자열)과 `location_fix.reason = 'incident'`인 행이다. 안심구역 알림은 좌표를 저장하지 않는다(LLD-0136 4.2).
4. **알림센터 옛 행**: `expires_at`이 비어 있는 행(종류가 없던 시절의 행)을 `created_at`에서 90일로 지워도 되는가.
5. **백업 보관 기간**: RDS 자동 백업을 며칠로 할 것인가. 수동 스냅샷을 허용하는가. 처리방침 문구.
6. **탈퇴 30일 동안의 복구**: 복구를 제공하는가. 제공하면 이름과 번호를 가리는 시점이 바뀐다.
7. **어르신 탈퇴 방식**: 본인이 바로 탈퇴하는가(권장), 요청을 남기고 운영자가 10일 안에 처리하는가(노션 최소안). 가족의 마지막 어르신이 탈퇴하면 가족방을 어떻게 하는가.
8. **가족 앨범**: 탈퇴자가 올린 사진과 영상, 다른 가족이 단 댓글, 다른 가족이 포인트로 연 잠금 해제를 어떻게 하는가.
9. **결제와 관리자 기록의 상한 삭제**: 5년, 2년이 지난 뒤 지우는 작업은 이 ADR 밖이다. 언제 만들지 정한다.
