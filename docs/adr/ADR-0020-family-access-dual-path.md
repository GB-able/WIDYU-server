# ADR-0020: 가족 접근 인가 이중 경로를 인정하고 정적 검증으로 강제

> Architecture Decision Record. 하나의 중요한 의사결정과 그 이유를 기록한다.

| 항목 | 값 |
| --- | --- |
| 상태 | Accepted |
| 날짜 | 2026-08-20 |
| 관련 | ADR-0002, ADR-0019, #491 |

## 맥락 (Context)

ADR-0002는 "모든 API마다 이 보호자가 해당 시니어의 가족인가를 수동으로 검증하면 코드 중복과 검증 누락 위험이 크다"는 이유로 `@ValidateFamilyAccess` AOP를 도입했다.

#489 리뷰에서 `GoalHomeController`의 `/guardian`·`/guardian/stats`에 이 애노테이션이 없는 것을 발견했다. 두 API는 `memberId`를 요청 파라미터로 받아 대상 회원을 그대로 조회하므로, 인증된 보호자라면 임의의 `memberId`로 다른 가족 시니어의 복약·걸음 데이터를 읽을 수 있었다.

`memberId`·`seniorId`를 받는 컨트롤러 핸들러 40개를 전수 확인한 결과 실제 구조는 아래와 같았다.

| 검증 방식 | 건수 |
| --- | ---: |
| `@ValidateFamilyAccess` (AOP) | 18 |
| 서비스 계층에서 직접 검증 | 16 |
| 검증 없음 | 2 (`GoalHomeController`) |

즉 ADR-0002가 없애려던 "수동 검증"이 절반 가까이 남아 있었고, `GoalHomeController`만 양쪽 어디에도 걸리지 않았다. 두 경로 모두 opt-in이므로 새 엔드포인트가 추가될 때 어느 쪽도 거치지 않으면 조용히 IDOR이 된다. 리뷰로는 잡히지 않는 종류의 누락이다.

## 결정 (Decision)

인가 경로를 하나로 통합하지 않고 **두 경로를 모두 정당한 것으로 인정하되, 어느 쪽도 거치지 않은 핸들러가 존재하면 빌드가 실패하도록** 정적 검증을 추가한다.

- `GoalHomeController`의 두 API에 `@ValidateFamilyAccess`를 추가한다.
- `ControllerFamilyAccessTest`가 `@RestController`를 스캔해 `memberId`·`seniorId`를 받는 핸들러를 열거하고, AOP 애노테이션도 없고 서비스 계층 검증 목록에도 없으면 실패한다.
- 서비스 계층에서 검증하는 16건은 **검증 위치를 근거 주석으로 명시해** 목록에 등록한다. 새 핸들러는 애노테이션을 붙이거나, 근거와 함께 목록에 등록해야 한다.
- Spring 컨텍스트를 띄우지 않고 `ClassPathScanningCandidateComponentProvider`만 사용한다. 신규 의존성은 없다.

## 고려한 대안 (Considered Options)

1. **애노테이션만 추가하고 끝낸다** — 이번 누락은 막지만 다음 누락은 못 막는다. 발견 경로가 사람의 리뷰뿐이라는 원인이 그대로 남아 채택하지 않는다.
2. **서비스 계층 검증 16건을 전부 AOP로 이관해 경로를 일원화한다** — 가장 깔끔하지만, 이들의 검증 조건이 단순 가족 관계가 아니다. 방장 권한(`assertIsLeader`), 대표 연락처 대상 여부, 관리자 역할 등이 섞여 있어 `@ValidateFamilyAccess` 하나로 표현되지 않는다. 애노테이션을 조건별로 늘리면 AOP 쪽이 다시 복잡해진다. 채택하지 않는다.
3. **기본 차단(default-deny) 후 명시적 허용** — 인터셉터에서 `memberId`를 받는 요청을 모두 막고 화이트리스트로 여는 방식. 누락이 런타임 403으로 드러나 가장 안전하지만, 기존 40개 핸들러의 동작을 한 번에 바꾸는 변경이라 회귀 위험이 크다. 채택하지 않는다.
4. **두 경로를 인정하고 정적 검증으로 강제한다** — 기존 코드를 건드리지 않으면서 누락만 차단하고, 검증 목록이 "어디서 어떻게 검증하는가"의 문서 역할도 한다. 채택한다.

## 결과 (Consequences)

### 긍정

- 검증을 빠뜨린 핸들러가 추가되면 CI에서 실패한다. 리뷰어의 주의력에 의존하지 않는다.
- 목록이 서비스 계층 검증 16건의 검증 위치를 한곳에 모아 인가 구조의 실제 지도 역할을 한다.
- 기존 핸들러 동작을 바꾸지 않으므로 회귀 위험이 없다.
- Spring 컨텍스트를 띄우지 않아 실행이 빠르고 신규 의존성이 없다.

### 부정 / 트레이드오프

- 목록 등록은 사람이 판단한다. 검증하지 않는 핸들러를 근거 없이 등록하면 테스트가 오히려 잘못된 안전감을 준다. 등록 시 검증 위치를 반드시 명시해야 하는 이유다.
- 파라미터 이름(`memberId`, `seniorId`)에 의존한다. 다른 이름으로 대상 회원을 받으면 스캔에 걸리지 않는다.
- 인가 경로가 두 갈래로 남는 근본 문제는 해결되지 않는다. 누락만 차단할 뿐이다.

## 후속 / 미결정

- 서비스 계층 검증 16건을 AOP로 일원화할지는 별도 이슈로 검토한다. 조건별 애노테이션 설계(방장 권한, 대표 연락처 등)가 선행되어야 한다.
- 대상 회원을 받는 파라미터 이름을 컨벤션으로 고정할지 검토한다.
