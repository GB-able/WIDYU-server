# ADR-0004: 미디어 업로드 전략 — 서버 직접 S3 업로드

| 항목 | 값 |
| --- | --- |
| 상태 | Accepted |
| 날짜 | 2026-07-05 |
| 관련 | ADR-0001, LLD-0006 |

## 맥락 (Context)

앨범 사진·영상, 복약 인증 이미지 등 여러 도메인에서 파일 업로드가 필요하다.
업로드 방식은 서버 경유 방식과 클라이언트 직접 업로드(Presigned URL) 두 가지 중 선택해야 한다.
영상 파일은 수십 MB에 달해 동기 처리 시 요청 블로킹이 길어지는 문제가 있다.

## 결정 (Decision)

**서버 경유 S3 업로드** 방식을 채택한다.

- 클라이언트: `multipart/form-data`로 파일을 서버에 전송
- 서버: `S3Service.uploadFile()`로 S3 버킷에 업로드 후 URL 반환
- 파일 크기 대용량(영상) 처리: `@Async` 전용 스레드풀로 비동기 파이프라인 처리
  - `MultipartFile` → `File` 변환 후 async 스레드에 전달 (요청 종료 후 `MultipartFile` 삭제 방지)
  - 앨범은 먼저 `PROCESSING` 상태로 저장하고 HTTP 202로 `albumId` 반환
  - 압축 → 길이 추출 → 썸네일 생성 → S3 업로드 순서로 처리
  - 완료 후 `Album.completeVideoProcessing()`으로 URL/썸네일/길이를 채우고 `ACTIVE` 전환
  - 완료 후 `AlbumCreatedEvent` 발행 → FCM 알림
  - 임시 파일은 `finally`에서 삭제
- 압축 완료 `File`을 썸네일 생성·길이 추출 단계에 직접 전달해 같은 파일을 반복 복사하지 않는다.

## 고려한 대안 (Considered Options)

1. **서버 경유 S3 업로드 (채택)** — 서버가 파일 수신 후 S3 업로드
   - 장점: 인증·파일 검증·압축을 서버에서 일괄 처리. 클라이언트 S3 자격증명 불필요. 영상은 @Async로 응답 블로킹 해소.
   - 단점: 서버 메모리·네트워크 2회 경유 (클라이언트→서버→S3). 대용량 파일 시 서버 리소스 소모.

2. **Presigned URL 직접 업로드** — 서버가 서명된 URL 발급, 클라이언트가 S3에 직접 업로드
   - 장점: 서버 리소스 절감, 대용량 파일에 유리
   - 단점: 미연결 오브젝트 정리 정책 필요. 파일 검증을 S3 Lambda 등 별도 인프라에서 처리해야 함. 현 팀 규모에서 운영 복잡도 과다.
   - **채택하지 않음**: 현재 사용자 규모에서 서버 경유 방식으로 충분하며, Presigned URL 방식으로 전환 시 별도 ADR/LLD 필요.

## 결과 (Consequences)

### 긍정
- 파일 검증(확장자, 크기)을 서버에서 일괄 처리 → 클라이언트 우회 불가
- 영상 업로드 비동기화로 API 응답 시간 53% 단축 (9.25s → 4.31s)
- 279MB 영상 기준 불필요한 디스크 쓰기 558MB 제거
- 영상 길이 추출 처리 시간 396ms → 113ms로 71% 단축
- S3 자격증명이 서버에만 존재

### 부정 / 트레이드오프
- `@Async` 스레드풀 기반이므로 서버 재시작 시 처리 중 작업 유실 가능. 현재 재시도 메커니즘 없음.
- 서버 네트워크 대역폭이 병목이 될 수 있음 (대용량 영상 동시 다수 업로드 시)

## 후속 / 미결정
- 서버 재시작 시 in-flight 업로드 처리 방안 (메시지 큐 도입 여부)은 트래픽 증가 후 재논의
- 미연결 미디어(업로드만 하고 기록 미생성) 정리 정책 — `docs/policy/policy-checklist.md` 확인
- **앨범 미디어 업로드 경로는 ADR-0015(Presigned Multipart 직접 업로드)로 대체되었다.** 그 외 도메인(복약 인증 이미지 등)은 본 ADR을 유지한다.
