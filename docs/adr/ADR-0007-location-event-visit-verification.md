# ADR-0007: 실시간 위치 이벤트 기반 방문인증 처리

| 항목 | 값 |
| --- | --- |
| 상태 | Accepted |
| 날짜 | 2026-07-10 |
| 관련 | LLD-0009, #387 |

## 맥락 (Context)

건강 일정 방문인증은 시니어의 실시간 위치와 건강 일정 좌표를 함께 사용한다.
위치 업데이트는 WebSocket 핫패스이며 수 초 간격으로 들어올 수 있고, 보호자 브로드캐스트와 Redis 위치 저장이 실패 없이 유지되어야 한다.

초기 구현은 `RealtimeLocationService`가 `HealthScheduleProgressService`를 직접 호출해 위치 업데이트 트랜잭션 안에서 건강 일정 DB 조회와 완료 처리를 수행했다.
이 방식은 location 도메인과 health 도메인의 직접 결합을 만들고, 건강 일정 로직 장애가 실시간 위치 업데이트와 브로드캐스트 실패로 전파될 수 있다.

## 결정 (Decision)

실시간 위치 업데이트 이후 방문인증 자동 완료는 **도메인 이벤트 기반 비동기 처리**로 분리한다.

- location 도메인: 위치 저장 후 `SeniorLocationUpdatedEvent(memberId, latitude, longitude)`를 발행한다.
- health 도메인: `HealthScheduleLocationEventListener`가 이벤트를 수신하고 `HealthScheduleProgressService.completeArrivedSchedules()`를 호출한다.
- 리스너는 `@Async`, `@EventListener`, `@Transactional`을 사용한다.
- 위치 핫패스는 건강 일정 DB 조회/완료 처리 결과에 의존하지 않는다.

## 고려한 대안 (Considered Options)

1. **RealtimeLocationService에서 HealthScheduleProgressService 직접 호출**
   - 장점: 구현이 단순하고 호출 흐름이 명시적이다.
   - 단점: location -> health 직접 결합이 생긴다. 건강 일정 DB 장애가 위치 업데이트와 브로드캐스트 실패로 전파된다. 위치 핫패스 지연이 커질 수 있다.

2. **ApplicationEventPublisher + 비동기 이벤트 리스너 (채택)**
   - 장점: 도메인 결합을 이벤트로 낮춘다. 위치 업데이트 핫패스와 건강 일정 자동 완료 처리를 격리한다. 기존 SafeZone 이벤트 패턴과 유사하다.
   - 단점: 자동 완료가 위치 업데이트 응답보다 늦게 반영될 수 있다. 비동기 처리 실패에 대한 재시도/보상 정책은 별도로 필요하다.

3. **메시지 큐(Kafka/RabbitMQ) 기반 처리**
   - 장점: 재시도, 버퍼링, 장애 격리에 유리하다.
   - 단점: 현재 트래픽과 운영 규모 대비 인프라 복잡도가 크다. 큐 운영/모니터링/중복 처리 정책이 추가로 필요하다.

## 결과 (Consequences)

### 긍정
- 실시간 위치 저장과 브로드캐스트가 건강 일정 DB 조회/완료 처리에 의해 지연되거나 실패하지 않는다.
- 위치 도메인과 건강 일정 도메인의 직접 의존을 제거한다.
- 향후 다른 도메인이 위치 업데이트 이벤트를 구독해도 location 서비스 변경 없이 확장할 수 있다.

### 부정 / 트레이드오프
- 이벤트 리스너 비동기 처리 실패 시 자동 완료가 누락될 수 있다.
- 위치 업데이트 직후 조회하면 자동 완료 반영이 아직 끝나지 않았을 수 있다.
- 현재는 애플리케이션 내부 이벤트이므로 서버 재시작 중 발생한 이벤트는 영속적으로 보존되지 않는다.

## 후속 / 미결정

- 방문 장소 도착 반경은 현재 75m 상수로 적용한다. 장소 유형별/사용자별 반경 정책이 필요하면 별도 정책으로 분리한다.
- 이벤트 처리 실패 재시도와 outbox/message queue 도입은 트래픽 증가나 자동 완료 누락 문제가 관측되면 재검토한다.
- 실시간 위치 TTL은 5분이다. 수동 완료 시 최신 위치가 없는 경우 실패하는 정책은 유지하되, 앱 위치 핑 주기와 함께 모니터링한다.
