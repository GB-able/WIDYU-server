# ADR-0013: 개인화 심박 AI 단건 계약 연동

> Architecture Decision Record. 하나의 중요한 의사결정과 그 이유를 기록한다.

| 항목 | 값 |
| --- | --- |
| 상태 | Accepted |
| 날짜 | 2026-07-26 |
| 관련 | LLD-0019, #446 |

## 맥락 (Context)

심박 AI가 15개 배열을 form 데이터로 받는 `/check` 계약에서 사용자별 단건 JSON을 받는 `/api/hr` 계약으로 변경되었다.
새 AI는 사용자별 초기 30개 데이터로 기준선을 만들고 각 측정값의 활동 상태와 시각을 사용하므로, 동일 사용자의 측정값을 시간순으로 전달해야 한다.
기존 앱과 백엔드는 WebSocket에서 15개 측정값을 한 배치로 주고받고 있다.

## 결정 (Decision)

앱의 15개 WebSocket 배치 계약은 유지하고 배치 수준 `context` 필드만 추가한다.
백엔드는 배치의 측정값을 시각 오름차순으로 정렬한 뒤 동일한 `memberId`를 `user_id`로 사용해 AI `/api/hr`에 순차 전송한다.
AI 응답의 `level`은 `NORMAL`, `CAUTION`, `EMERGENCY` 상태로 저장·노출하며, 기존 `ANOMALY`는 과거 데이터 호환을 위해 유지한다.
즉시 위급상황 저장은 `alert=true`이면서 `level=EMERGENCY`인 응답이 배치에 하나 이상 있을 때만 수행한다.

## 고려한 대안 (Considered Options)

1. **앱이 AI 단건 계약에 맞춰 한 건씩 전송** — 서버 구현은 단순하지만 WebSocket 호출 빈도와 앱 계약 변경이 커진다.
2. **15개를 병렬 전송** — 호출 시간은 줄지만 사용자 기준선과 지속 시간 판별 순서가 깨질 수 있다.
3. **기존 배치를 서버에서 순차 단건 호출로 변환** — 앱 변경을 `context` 추가로 제한하면서 AI의 사용자별 시계열 순서를 지킨다.

## 결과 (Consequences)

### 긍정

- 기존 WebSocket 배치와 조회 응답 구조를 유지한다.
- 사용자별 기준선과 30초 지속 판별에 필요한 측정 순서를 보존한다.
- `CAUTION`을 즉시 위급상황으로 오인하지 않는다.

### 부정 / 트레이드오프

- 배치 하나당 AI 요청이 15회 발생한다. 다만 실측(2026-08-18, 로컬 컨테이너)에서 15회 순차 호출은 14~15ms로 지연 기여가 미미했다. 최신 심박 조회의 수십 초 지연은 배치 저장 시점에만 갱신되는 구조, 즉 워치의 배치 수집 주기에서 비롯된다.
- AI 호출 도중 한 건이라도 실패하면 기존 정책대로 배치 전체 저장이 수행되지 않는다.
- 여러 서버 인스턴스에서 같은 사용자의 배치를 동시에 처리하는 순서는 보장하지 않는다.
- `context`를 배치 수준 단일 값으로 받으므로 15개 측정값의 활동 상태가 배치 내에서 달라져도 구분하지 않는다.
- AI 판정 계층은 `context`로 갈린다. `REST`는 L1(개인 기준선), 나머지는 L0(고정 임계값)이다. 앱이 `context`를 보내지 않으면 `UNKNOWN`으로 정규화되어 이 ADR이 전제한 개인화가 적용되지 않는다.
- 다만 실측에서 L1 경로는 190bpm을 60초 지속시켜도 `EMERGENCY`를 반환하지 않은 반면, L0 경로는 31초째 반환했다. `context`를 보내도록 앱을 바꾸면 개인화는 얻지만 휴식 중 위급 감지를 잃을 수 있다. 확인 전까지 현행(`UNKNOWN`)을 유지한다.
- AI는 bpm 0과 300을 400으로 거부한다. 서버 검증을 1~299로 맞추지 않으면 워치 미착용 시 올라오는 0 하나가 배치 15개 전체를 실패시킨다.
- `level`만 저장하고 `reason`·`layer`·`baseline_source`를 폐기하므로, 이상 판정의 사유(서맥·빈맥·개인 기준 이탈)와 개인화 적용 여부를 사후에 확인할 수 없다.

## 후속 / 미결정

- `CAUTION` 빈도 기반 알림과 보호자용 순화 메시지는 제품 정책 확정 후 별도 ADR/LLD에서 결정한다.
- `context=REST`에서 위급 상황이 감지되지 않는 원인을 AI 담당자에게 확인해야 한다. 이 답변이 `context` 전송 정책의 전제다.
- 앱이 실제로 `context`를 전송하는지 확인이 필요하다. 서버 로그의 `rawContext`로 관측한다.
- `reason` 영속화 여부는 보호자 화면·알림에 이상 사유를 노출할지 결정된 뒤 판단한다.
