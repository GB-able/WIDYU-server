# LLD-0130: 보호자가 위치를 볼 때마다 어르신께 바로 알리기 (10분 묶기, 아침 요약 끄기)

> Low-Level Design. 이 문서는 해당 기능 구현과 PR 본문의 **오라클(ground truth)** 이다.

## 1. 목적 / 배경

보호자가 어르신 위치를 보면 서버는 열람 기록을 한 줄 남기고 어르신에게 「위치 조회 알림」 푸시를 보낸다(LLD-0056). 그런데 지금은 세 가지 경우에 알림을 바로 보내지 않는다.

1. 같은 보호자가 10분 안에 다시 보면 푸시를 보내지 않고 다음 날 아침 요약으로 넘긴다.
2. 매일 아침 9시에 그동안 알리지 않은 기록을 어르신별 요약 한 건으로 보낸다.
3. 「위치 본 사실을 모아서 받기」에 동의한 어르신은 바로 받지 못하고 아침 요약으로만 받는다.

위치정보법은 개인위치정보를 제3자에게 제공할 때마다 본인에게 **즉시** 알리게 한다. 모아서 알리는 것은 법이 정한 단위, 즉 10회마다 또는 10일, 20일, 30일 주기로 묶을 때만 허용된다. 위치정보지원센터는 10월 8일 질의에 이렇게 답했다.

- 「10분에 1회」 같은 기준은 없다. 실제로 위치를 보낸 횟수로 센다.
- 하루 한 번 묶어 알리는 것은 본인이 동의해도 안 된다.

지금 동작은 세 경우 모두 이 답과 맞지 않는다. 그래서 열람마다 바로 알리고, 아침 요약을 끈다. 「모아서 받기」를 법정 단위(10회, 10일, 20일, 30일)로 다시 만드는 일은 이번 범위가 아니다. 가입 화면에서도 그 항목을 빼기로 했다(앱 작업).

## 2. 범위

### In scope
- 변경 모듈: widyu-api
- 묶는 시간(`location-access.immediate-cooldown-min`, 환경변수 `LOCATION_ACCESS_IMMEDIATE_COOLDOWN_MIN`) 기본값 10 → 0
- `LocationAccessLogService.record`가 `LOCATION_NOTICE_BATCHED` 동의를 보지 않고 항상 바로 알림 경로를 탄다
- 아침 요약 cron(`location-access.digest-cron`, 환경변수 `LOCATION_ACCESS_DIGEST_CRON`) 기본값 `0 0 9 * * *` → `-`(Spring 예약어, 스케줄 등록 안 함)
- 서버가 뜬 뒤 한 번, 남은 미통보 기록을 요약 발송(6절 이전 기록 처리)
- ADR-0036 결정 4 갱신 메모, LLD-0056과 backend/CLAUDE.md 설명 갱신

### Out of scope
- 법정 단위(10회, 10일, 20일, 30일) 모아서 알림. 필요해지면 따로 설계한다
- `ConsentKey.LOCATION_NOTICE_BATCHED` 삭제. 앱이 아직 보낼 수 있고 동의 기록은 사실로 남겨야 하므로 값은 그대로 받고 저장한다. 알림 방식 결정에만 쓰지 않는다
- 가입 화면의 「모아서 받기」 항목 제거(앱)
- 실시간 지도(STOMP 구독)에서 알림 횟수를 어떻게 셀지. 지금은 구독 한 번이 열람 한 번이다(LLD-0056 5.1). 10절의 조사 결과로 따로 정한다
- `LocationAccessLogRepository`, 관리자 API 변경

## 3. 인터페이스 / API

API 변경 없음. 어르신이 받는 푸시 문구도 그대로다.

- 바로 알림: 제목 「위치 조회 알림」, 본문 「{보호자 이름}님이 내 위치를 확인했어요」
- 시작 시 한 번 요약: 「지난 기간 보호자 {n}명이 위치를 {m}회 확인했어요」(기존 다이제스트 문구)

## 4. 데이터 모델

테이블 변경 없음. 설정 기본값만 바뀐다.

```yaml
location-access:
  immediate-cooldown-min: ${LOCATION_ACCESS_IMMEDIATE_COOLDOWN_MIN:0}
  digest-cron: ${LOCATION_ACCESS_DIGEST_CRON:-}
```

`-`는 `Scheduled.CRON_DISABLED`다. 값이 `-`면 Spring이 해당 cron 작업을 등록하지 않는다.

## 5. 처리 흐름

### 5.1 열람 기록과 바로 알림 — `LocationAccessLogService.record`

1. 본인 조회면 끝낸다(변경 없음).
2. 어르신 회원 행을 잠그고 열람 기록을 저장한다(변경 없음).
3. **동의 확인을 하지 않고** 바로 알림으로 간다. `ConsentService` 의존을 뺀다.
4. 같은 보호자에게 `now - 묶는 시간` 이후 알린 기록이 있으면 건너뛴다. 기본값 0분이면 기준 시각이 `now`라 이전 알림이 걸리지 않으므로 매번 FCM 한 건을 등록하고 `notified_at = now`를 채운다.

묶는 시간 설정과 그 판정 코드는 남긴다. 법정 단위 묶음을 설계할 때까지 운영값을 0으로 두는 스위치로만 쓴다.

### 5.2 아침 요약 끄기 — `LocationAccessDigestScheduler.sendDigest`

`@Scheduled(cron = "${location-access.digest-cron}")`는 그대로 두고 기본값만 `-`로 바꾼다. 클래스와 선점 로직(`LocationAccessDigestSender`)은 6절의 이전 기록 처리에 다시 쓴다.

### 5.3 시작 시 한 번 요약 — `LocationAccessDigestScheduler.flushOnStartup`

`@Scheduled(initialDelay = 60_000)`로 서버 시작 1분 뒤 **한 번만** `sendDigest()`를 실행한다. Spring 6.1부터 `initialDelay`만 준 `@Scheduled`는 반복하지 않는 1회 작업이다. `SchedulerConfig`의 `widyu.scheduling.enabled`를 그대로 따르므로 테스트 컨텍스트에서는 돌지 않는다. 1분을 두는 이유는 FCM 초기화와 기동 직후 부하가 지난 뒤 보내기 위해서다.

선점은 기존과 같다. 어르신별로 조건부 UPDATE(`notified_at IS NULL` → `now`)로 집고, 같은 트랜잭션에서 FCM을 등록한다. 서버가 여러 대여도 먼저 집은 쪽만 보낸다. 등록이 실패하면 선점이 롤백되어 그 기록은 다음 서버 시작 때 다시 시도한다.

## 6. 이전 기록 처리와 배포 순서

### 무엇이 문제인가

배포 시점에 `notified_at IS NULL`인 기록이 남아 있을 수 있다. 10분 안 재조회로 건너뛴 기록, 「모아서 받기」 동의자의 기록이다. 지금까지는 다음 날 아침 9시 요약이 이 기록을 가져갔다. 요약을 끄기만 하면 이 기록은 영영 알려지지 않는다.

순서도 문제다. 요약을 먼저 끄고 바로 알림을 나중에 켜면, 그사이 「모아서 받기」 동의자와 10분 안 재조회는 아무 알림도 받지 못한다.

### 어떻게 막는가

1. **바로 알림과 요약 끄기를 한 배포에 넣는다.** 새 버전이 뜬 순간부터 모든 열람은 바로 알림을 타므로 새 미통보 기록이 생기지 않는다. 요약만 꺼진 구간이 없다.
2. **남은 기록은 시작 1분 뒤 한 번 요약으로 보낸다(5.3).** 배포 직전까지 쌓인 미통보 기록이 어르신별 한 건으로 나간다. 이미 늦은 알림이지만 영영 안 가는 것보다 낫고, 배포 뒤 첫 아침 9시를 기다리지 않는다.

검토한 다른 방법은 이렇다.

- **배포 직전 운영자가 요약을 손으로 한 번 실행.** 실행 입구(관리자 API 등)가 없어 새로 만들어야 하고, 사람이 빠뜨리면 그대로 사라진다. 채택하지 않았다.
- **바로 알림 경로가 그 어르신의 이전 미통보 기록도 함께 처리.** 배포 뒤 다시 열람되지 않는 어르신의 기록은 남는다. 채택하지 않았다.
- **아침 요약을 켠 채로 두기.** 바로 알림이 모든 기록을 처리하면 요약은 대상이 없어 사실상 동작하지 않는다. 다만 「하루 한 번 묶음」 기능이 운영에 살아 있는 것 자체가 결정과 맞지 않아 기본값은 끈다.

### 남는 한계

- 서버가 여러 대이고 배포가 한 대씩 바뀌면, 옛 버전이 아직 도는 동안 생긴 미통보 기록은 새 버전의 시작 요약이 이미 지나간 뒤일 수 있다. 그 기록은 다음 서버 시작 때 나간다. 저장소의 compose 설정은 앱 컨테이너 한 대를 바꾸는 방식이라 해당 구간이 없다.
- 운영 환경변수가 `LOCATION_ACCESS_IMMEDIATE_COOLDOWN_MIN`이나 `LOCATION_ACCESS_DIGEST_CRON`을 직접 지정하고 있으면 기본값 변경이 적용되지 않는다. 운영 반영 전에 두 값이 비어 있거나 각각 `0`, `-`인지 확인한다. 묶는 시간이 0보다 크게 남으면 건너뛴 기록은 서버를 다시 시작할 때만 나간다.

## 7. 인수조건 (Acceptance Criteria)

- [ ] 같은 보호자가 연달아 봐도, 묶는 시간이 0이면 열람마다 FCM 한 건과 `notified_at`이 남는다.
- [ ] `LOCATION_NOTICE_BATCHED`에 동의한 어르신도 열람 시점에 FCM을 받는다. 알림 방식 결정에서 동의 기록을 읽지 않는다.
- [ ] `application.yml` 기본값이 `immediate-cooldown-min: 0`, `digest-cron: -`다.
- [ ] `flushOnStartup`은 `initialDelay`만 가진 1회 작업이고, 실행하면 미통보 기록을 어르신별로 요약 발송한다.
- [ ] 기존 다이제스트 선점과 롤백 테스트(`LocationAccessDigestSenderTest`)가 그대로 통과한다.
- [ ] `verify.sh`가 통과한다.

## 8. 영향 범위 / 마이그레이션

- 어르신이 받는 위치 조회 푸시 수가 늘어난다. 보호자가 홈 화면을 열 때마다 어르신 수만큼(`HOME_OUTING`), 지도 화면에서 구독할 때마다 한 건씩 나간다.
- DB 마이그레이션 없음.
- 운영 반영 순서: 운영 환경변수 두 개 확인 → 배포 → 시작 1분 뒤 로그 `위치 열람 요약 통보` 또는 `위치 열람 요약 통보 대상 없음` 확인.

## 10. 참고

### 보호자 지도 화면을 10분 열어 두면 위치가 몇 번 가는가 (코드 조사, 2026-11-10)

- **열람 기록과 알림:** STOMP로 `/topic/location/senior/{id}`를 구독할 때 `JwtChannelInterceptor.handleSubscribe`가 한 번 기록한다(`WS_SUBSCRIBE`). 구독을 유지하는 동안 흘러가는 위치 메시지는 기록하지 않는다.
- **서버가 보내는 주기:** 서버에는 정해진 주기의 방송이 없다. 어르신 앱이 `/app/location/update`로 위치를 보낼 때마다, 최신 위치보다 나중에 잰 값이면 그 즉시 구독자에게 한 번 방송한다(`RealtimeLocationService.broadcastQuietly`). 4분마다 도는 `refreshLocationTtl`은 Redis 만료만 늘리고 방송하지 않는다.
- **어르신 앱이 보내는 주기:** 서버가 센서 수집 설정으로 내려주는 권고값은 이동 중 5초(`location-move-sec`), 정지 중 60초(`location-keepalive-sec`)다(`application-sensor.yml`, `GET /api/v1/sensor/config`). 이 값대로 보내면 10분에 정지 시 약 10번, 계속 이동 시 약 120번 방송된다. 앱이 실제로 이 값을 따르는지는 앱 확인이 필요하다.
- **REST:** 지도 화면이 `GET /api/v1/location/realtime/senior/{id}`(최신 위치), `/senior/{id}/trail`(이동 경로), `/seniors`(목록)를 몇 초마다 다시 부르는지는 서버 코드로 알 수 없다(앱 확인 필요). 부를 때마다 기록과 알림이 한 건씩 생긴다.
