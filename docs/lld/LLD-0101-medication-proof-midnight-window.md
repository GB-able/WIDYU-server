## 1. 목적 / 배경

복약 인증은 알람 시각 전후 30분 안에만 받는다(backend 복약 불변식, LLD-0007·0038). 기존 `MedicationProofTransactionService.validateScheduleTime`은 기준 알람을 항상 `now.toLocalDate().atTime(alarmTime)`, 즉 **오늘 날짜의 알람**으로 잡았다. 창이 자정을 넘으면 절반이 거부됐다.

- 알람 23:45의 창은 23:15~00:15이지만 00:00~00:15 인증은 오늘 23:45와 비교되어 400이었다.
- 알람 00:10의 창은 전날 23:40~00:40이지만 23:40~23:59 인증은 오늘 00:10과 비교되어 400이었다.

복약 알림 스케줄러는 알람 날짜 기준으로 +10·+20분 미인증 푸시를 보낸다. 23:45 알람이면 00:05에 인증을 요청하고 서버는 그 인증을 거절했다. 중복 검사와 `verified_date` 저장도 "지금 날짜"라, 창만 고치면 어제 알람의 인증이 오늘 분으로 저장된다.

## 2. 범위

### In scope
- 변경 모듈: widyu-api (goal/medicineschedule), widyu-domain (`MedicationProof`)
- 복용 기준일 규칙: 인증 시각이 알람 ±30분 안에 드는 알람의 날짜
- 유효 스케줄 검사, 중복 인증 검사, `verified_date` 저장, 즉시 적립의 하루 완료 판정을 복용 기준일로 통일
- `MedicationProof.create`가 인증 시각과 복용 기준일을 받는다(`@PrePersist` 파생 제거)
- 다음 날 복용분 인증이 있는 회원의 자정 전 스케줄 등록·수정·삭제 차단(5-3)

### Out of scope
- 읽기 쪽의 `verified_date` 전환 — #872(PR #875, develop 머지됨)
- 알람 동기화 `completed`에 다음 날 기준일 인증을 넣는 것 — 9절
- 건강 일정의 같은 자정 경계 문제 — #869
- 인증 창 길이(30분)·메시지 문구 변경

## 3. 인터페이스 / API

HTTP API는 바뀌지 않는다. `POST /api/v1/goals/medicine-schedules/{scheduleId}/verify`가 받아들이는 시각 범위만 넓어진다(자정을 넘는 창의 나머지 절반). 오류 코드·메시지는 그대로다.

## 4. 데이터 모델

`medication_proof.verified_date`(DATE, NOT NULL, 기존 컬럼)의 의미를 "`verified_at`의 날짜"에서 **"복용 기준일(인증한 알람의 날짜)"**로 바꾼다. 스키마 변경은 없다. 자정을 넘는 창의 인증만 두 값이 하루 다르고, 그 밖에는 같다. 기존 행은 모두 `verified_date = DATE(verified_at)`이다.

`MedicationProof.create(schedule, member, imageUrls, verifiedAt, verifiedDate)`로 두 값을 서비스가 넘긴다. `@PrePersist` 파생은 없앤다(값이 둘로 갈라질 수 있어 파생할 수 없다).

ERD-0001의 `MedicationProof`에 `verifiedDate`와 의미를 적는다.

## 5. 처리 흐름

### 5-1. 복용 기준일 (`MedicationProofTransactionService.resolveDoseDate`)

```
for d in [오늘-1, 오늘, 오늘+1]:          // now.toLocalDate() 기준
    alarmAt = d.atTime(schedule.alarmTime)
    if alarmAt - 30분 <= now <= alarmAt + 30분:
        schedule.isEffectiveOn(d)가 아니면 400 "오늘 유효하지 않은 약 복용 스케줄입니다."
        return d
400 "약 복용 인증은 알람 시간 전후 30분 이내에만 가능합니다."
```

창 길이(60분)가 하루보다 훨씬 짧아 맞는 날짜는 많아야 하나다. 경계는 기존과 같이 양 끝을 포함한다.

| 알람 | 인증 시각 | 복용 기준일 |
| --- | --- | --- |
| 23:45 | 8/11 00:05 | 8/10 |
| 00:10 | 8/10 23:50 | 8/11 |
| 08:00 | 8/10 08:20 | 8/10 (기존과 같음) |
| 23:45 | 8/11 00:16 | 거부 |
| 23:50 | 8/10 23:59:59, 8/11 00:00, 00:10, 00:20 | 8/10 |
| 00:10 | 8/10 23:40, 23:59:59, 8/11 00:00, 00:40 | 8/11 |

### 5-2. 인증 (업로드 전 1차 검증·업로드 후 저장 모두)

1. 소유자 검증
2. `resolveDoseDate(schedule, now)` — 유효 스케줄 검사 포함
3. 중복 검사 `existsByMedicineScheduleAndVerifiedDate(schedule, doseDate)`
4. (저장 단계) `MedicationProof.create(..., now, doseDate)` → `saveAndFlush`. 유일 제약 `(medicine_schedule_id, verified_date)`이 같은 알람 날짜의 동시 중복을 막는다
5. (저장 단계) 즉시 적립: `countByMemberAndVerifiedDate(member, doseDate)`와 `countEffectiveByMemberAndDate(member, ACTIVE, doseDate)`로 그 알람 날짜의 증분을 계산한다(LLD-0038의 계산식 그대로)

트랜잭션 경계는 LLD-0037·0038과 같다. 저장 단계의 `now`는 **회원 행 잠금을 얻은 뒤** 읽는다. 창 끝에 들어온 요청이 잠금을 기다리는 동안 창이 닫히면 거부한다(기존 코드도 잠금 뒤 시각을 썼다). 테스트가 시각을 고정할 수 있도록 public 메서드는 `Clock.systemDefaultZone()`을 넘기는 패키지 전용 오버로드를 부른다.

### 5-3. 다음 날 복용분 인증 뒤의 스케줄 등록·수정·삭제

LLD-0113(당일 적용)에서 변경의 적용일은 알람마다 "오늘 끝났는지"로 정한다. 23:30 이후 다음 날 00:30 이전 알람을 미리 인증할 수 있는 시간에는 그 알람을 포함해 오늘 알람 대부분이 이미 끝난 상태다(인증 가능 시간이 지났거나 오늘 인증함). 그래서 이 시간의 수정, 삭제와 지난 시각 등록은 대부분 **내일부터** 적용되고, 아직 안 끝난 알람의 변경도 오늘부터 이어져 내일 구성을 바꾼다. 미리 인증하면(복용 기준일 = 내일) 그 시점의 내일 일정 구성으로 즉시 적립(완주 보너스 포함)이 계산되므로, 그 뒤 자정 전에 내일 구성이 바뀌면 어긋난다.

- 등록: 내일 일정이 하나뿐일 때 미리 인증해 30p(보너스 포함)를 받은 뒤 일정을 더하면, 더한 일정 인증에서 보너스가 다시 나가 내일 총 60p가 된다(정상 40p).
- 삭제: 미인증 일정을 지우면 내일 보너스가 누락되거나, 인증한 버전이 오늘까지만 유효해져 내일 인증이 유효하지 않은 버전에 남는다. 읽는 쪽은 그날 유효한 스케줄의 인증만 보지만 하루 인증 수(`countByMemberAndVerifiedDate`)에는 남아 다른 일정 적립이 줄어든다.
- 수정: 끝난 알람의 수정은 옛 버전을 오늘까지 마감하고 내일 시작 새 버전을 만든다. 미리 한 인증은 옛 버전에 남아 내일 유효하지 않은 버전의 인증이 되고, 새 버전은 내일 다시 인증할 수 있다(같은 복약의 이중 인증).

그래서 `MedicineScheduleService.createSchedule`·`updateSchedule`·`deleteSchedule`은 회원 행을 잠근 뒤 `existsByMemberAndVerifiedDateAfter(member, today)`이면 400 "다음 날 복용분을 이미 인증해 자정이 지난 뒤에 스케줄을 등록/수정/삭제할 수 있습니다."로 거부한다. 인증 저장도 같은 회원 행을 잠그므로 둘의 순서가 정해진다(변경이 먼저면 인증이 바뀐 내일 구성으로 계산되고, 인증이 먼저면 변경이 막힌다). 차단 구간은 그 인증 시각부터 자정까지(최대 30분)이고, 자정이 지나면 그 인증은 "오늘" 분이라 기존 규칙대로 처리된다. 인증·포인트를 지우거나 옮기지 않는다.

### 5-4. 읽기

#872 이후 읽는 쪽(일자별·월별 현황, 목표 홈, 시니어·보호자 홈, 복약 알림 스케줄러, 알람 동기화)은 `verified_date`로 날짜를 판정한다. 따라서 8/11 00:05에 한 8/10 23:45 알람 인증은 8/10의 완료로 보이고, 8/10 23:45 알람의 +30분(00:15) 보호자 미복용 알림이 나가지 않으며, 8/11 23:45 스케줄은 그날 저녁까지 미완료다.

## 6. 예외 / 에러 처리

| 상황 | 처리 |
|------|------|
| 어떤 날짜의 알람 ±30분에도 들지 않음 | 400 "약 복용 인증은 알람 시간 전후 30분 이내에만 가능합니다." (기존 문구) |
| 맞는 알람 날짜에 스케줄이 유효하지 않음 | 400 "오늘 유효하지 않은 약 복용 스케줄입니다." (기존 문구) |
| 같은 알람 날짜에 이미 인증 | 400 "오늘은 이미 해당 약 복용을 인증했습니다." (기존 문구, 선검증·유일 제약 양쪽) |
| 회원 잠금 대기 중 창이 닫힘 | 400 시간창 문구 (잠금 뒤 시각으로 검증) |
| 다음 날 복용분 인증이 있는 회원의 자정 전 스케줄 등록·수정·삭제 | 400 "다음 날 복용분을 이미 인증해 자정이 지난 뒤에 스케줄을 등록/수정/삭제할 수 있습니다." |

검사 순서가 "유효일 → 시간창"에서 "시간창 → 유효일"로 바뀐다. 유효일은 시간창이 정한 날짜로만 판단할 수 있기 때문이다. 창 밖이면서 유효하지 않은 스케줄은 이제 시간창 오류 문구를 받는다.

## 8. 영향 범위 / 마이그레이션

- 스키마·데이터 변경 없음. 기존 행은 그대로 유효하다.

- #1059 이후 오늘 복약 현황은 `TodayMedicationQuery`가 `verified_date`로 고르므로 추가 변경이 없다. #1053(인증 사진 검사)은 저장 전 단계라 영향이 없다.
- 열린 PR #944(#940, 완주 보너스 하루 1회)는 `verifyMedication`의 같은 적립 구간을 고친다. 나중에 머지되는 쪽이 `now.toLocalDate()` 자리를 `doseDate`로 맞춘다.

### 8-1. LLD-0113(당일 적용)과 만나는 경우 (2026-11-16 재점검)

LLD-0113의 "오늘 끝났는지"는 오늘 날짜 알람과 `verified_date = 오늘` 인증으로 판정한다. 복용 기준일을 쓰면 두 규칙은 아래처럼 함께 성립한다. 둘 다 지킬 수 없는 경우는 찾지 못했다.

| 상황 | LLD-0113 판정 | 결과 |
| --- | --- | --- |
| 00:15에 어제 23:50 알람을 인증(기준일 어제)한 뒤 그 알람을 수정, 삭제 | 오늘 23:50은 안 끝남 → 오늘부터 | 옛 버전이 어제까지 유효해 어제 인증이 그대로 남는다. 차단하지 않는다 |
| 어제 23:50에 오늘 00:10 알람을 미리 인증(기준일 오늘)한 뒤 00:20에 수정, 삭제 | 오늘 인증 있음 → 끝남 → 내일부터 | 오늘 인증이 오늘까지 유효한 옛 버전에 남는다. 차단하지 않는다 |
| 23:50에 내일 00:10 알람을 미리 인증(기준일 내일)한 뒤 자정 전에 그 알람을 수정, 삭제 | 오늘 00:10 창이 지남 → 끝남 → 내일부터 | 차단하지 않으면 내일 인증이 내일 유효하지 않은 옛 버전에 남는다. **5-3 차단** |
| 23시대에 0시 10분 알람 등록, 수정 | 오늘 창이 지남 → 내일부터 | 새 버전은 내일 유효하므로 지금(내일 분 창 안) 인증할 수 있고, 오늘까지 마감된 옛 버전은 거부한다 |
| 00:05에 어제 23:45 알람이 미인증인 채 삭제 | 오늘 23:45는 안 끝남 → 오늘부터 중단(어제까지 마감) | 지난 날짜 기록은 LLD-0113이 건드리지 않으므로 어제 분은 00:15까지 옛 ID로 인증할 수 있다 |

LLD-0061(다음 날 적용) 시절의 5-3 근거는 "모든 변경이 내일부터"였다. LLD-0113 이후에는 "미리 인증한 알람은 오늘 창이 이미 지나 끝난 알람이라 그 알람의 변경은 여전히 내일부터 적용된다"가 근거다. 차단 범위(회원 단위, 등록 포함)는 2026-10-30 사용자 결정대로 유지한다. 등록 차단이 막는 보너스 중복은 #944가 머지되면 따로 막히지만, 수정, 삭제의 버전 어긋남은 남으므로 차단은 계속 필요하다.

## 9. 미결정 사항 (Open Questions)

- [x] 다음 날 복용분을 미리 인증한 회원의 자정 전 스케줄 등록·수정·삭제를 이 LLD는 **차단**한다(5-3, Codex 검수 지적 대응). LLD-0113 이후에도 이 시간대 변경은 대부분 내일부터 적용돼 같은 어긋남이 생기므로 차단을 유지했다(2026-10-30). 대안은 (a) 변경 뒤 내일 적립을 다시 계산해 보정하는 것, (b) 다음 날 복용분 인증에는 적립을 미루고 자정 뒤 확정하는 것, (c) 다음 날 복용분 미리 인증 자체를 막는 것(00:10 알람의 23:50 인증 불가)이다. (a)는 활동 보상 환수 경로가 없고, (b)는 LLD-0038 즉시 적립과 다르며, (c)는 이번 이슈의 완료 조건과 다르다. 차단 구간은 최대 30분이다. **사용자 결정(2026-10-30): 차단 유지로 확정.**
  - 범위 밖: 완주 보너스가 하루에 두 번 나갈 수 있는 문제는 이 차단과 원인이 다르다. 포인트 규칙이 "그날 인증 수 = 그날 유효 일정 수"일 때마다 보너스를 주는데, LLD-0113 이후 같은 날 일정이 늘 수 있어 낮에도 생긴다(일정 1개 인증 30p → 같은 날 일정 추가 → 그 인증에서 보너스 재지급). 자정 차단이 풀린 00:01 등록도 같은 원인이다. 별도 이슈 #940에서 보너스를 하루 1회로 고친다.

- [ ] 알람 동기화(`GET /alarm-sync`, LLD-0037)의 `completed`는 "오늘(Asia/Seoul) 인증된 `scheduleId:날짜`"다. 00:30 이전 알람을 전날 밤(23:30 이후)에 인증하면 복용 기준일이 다음 날이라 `completed`에 들어가지 않고, 앱이 그 사이 다시 동기화하지 않으면 기기 알람이 그대로 울릴 수 있다. 서버 푸시(+10·+20분, 보호자 +30분)는 `verified_date`로 걸러져 나가지 않는다. `completed`에 다음 날 기준일 키를 함께 넣을지는 앱 계약 변경이라 앱과 정한다.
