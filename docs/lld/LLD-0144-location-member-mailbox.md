# LLD-0144: 회원별 위치 우편함으로 한 회원의 몰림이 공용 수신 스레드를 붙잡지 않게 한다

> Low-Level Design. 이 문서는 해당 기능 구현과 PR 본문의 **오라클(ground truth)** 이다.

## 1. 목적 / 배경

위치 처리는 STOMP 수신 스레드(최대 16개)에서 돌았다. 회원별 순서 잠금(`MemberLocationSequencer`)은 같은 회원 처리를 하나로 만들지만, 잠금을 기다리는 요청도 수신 스레드를 쥐고 있었다. 지금까지보다 늦게 잰 위치는 대기 수 상한을 우회하고, 밀린 위치도 더 최근 위치가 반영될 때까지 기다렸다(LLD-0140 9절). 그래서 한 회원이 측정 시각을 늘려 가며 몰아 보내면 그 회원이 수신 스레드를 모두 차지해 다른 회원의 위치까지 최대 3초(잠금 대기 한도) 밀렸다.

재현(결정적 테스트, 8절): 회원 A의 판정을 붙잡고 A가 31건을 보내는 동안 회원 B의 1건은 수정 전(7d25b2b6) 2초 안에 ACK를 받지 못했고, 수정 뒤 31ms에 `APPLIED`를 받았다.

## 2. 범위

### In scope

- 회원별 우편함(`MemberLocationMailbox`)과 위치 전용 실행기(`websocketLocationExecutor`)
- 수신 조율자 분리: `prepare`(수신 스레드), `process`(작업 스레드), `submit`(STOMP 진입점). 동기 `receive`, `applyRealtime`은 그대로 둔다(같은 처리, 테스트와 내부 호출용).
- ACK, 오류, 과부하를 원래 발신 세션에 보내는 경로(`WebSocketWorkDispatcher` 재사용)

### Out of scope

- ACK 의미(`APPLIED`, `SKIPPED`, `REJECTED`, ACK 없음) 변경. 이번에 바뀌지 않는다.
- 다중 인스턴스 순서 보장, 앱 코드, 안전구역 규칙, 위치 원본 저장(다시 넣지 않는다)

## 3. 설계

### 3.1 흐름

```
STOMP 수신 스레드 ─ prepare: 파싱, 입력 검증, 본인 확인, 순서 시각 한 번 결정 (DB, Redis 없음)
   ├ 입력 오류 → 바로 REJECTED (컨트롤러가 @SendToUser로 보냄)
   └ 우편함.submit(회원, 작업) → 바로 돌아감
위치 실행기(8 스레드) ─ 회원 차례 하나씩
   └ process: 회원 순서 잠금 → 최신 비교 → judge(트랜잭션) → project(최신 위치, 경로, 방송) → ACK 결정
      → 발신 세션에 ACK, 밀린 항목 정리, 할 일이 남았으면 대기열 맨 뒤로 다시 들어감
```

### 3.2 회원 상자와 상한

| 항목 | 상한 | 넘을 때 |
| --- | --- | --- |
| 회원별 실행 | 1 | 실행 중이면 차례를 다시 넣지 않는다 |
| 회원별 최신 대기 | 1 | 더 늦게 잰 위치가 오면 교체하고, 교체된 작업은 밀린 항목이 된다 |
| 회원별 밀린 항목 | `location.ingest.max-waiting-per-member` (16) | 가장 먼저 들어온 항목을 과부하로 끝낸다(ACK 없음, `TEMPORARILY_BUSY`) |
| 활성 회원(상자) | `location.ingest.max-members` (1024) | 새 회원의 위치를 과부하로 끝낸다 |
| 전체 보관 작업(실행+대기+밀린) | `location.ingest.max-queued` (4096) | 새 위치를 과부하로 끝낸다 |
| 실행기 스레드 | `websocket.executor.location.threads` (8) | 대기열 용량 = 활성 회원 상한, AbortPolicy |

- 실행기 대기열에는 회원마다 차례 하나만 들어간다. 그래서 대기열 용량을 활성 회원 상한과 같게 두면 재등록이 거절되지 않는다(종료 중 제외). 수신 스레드에서 대신 실행하지 않는다(CallerRuns 없음).
- 작업 하나를 끝낸 회원은 더 할 일이 있으면 대기열 맨 뒤로 다시 들어간다. 한 회원이 몰아 보내도 실행기에서 다른 회원과 번갈아 실행된다.
- 실행기 스레드 8은 Hikari 풀(10)보다 작다. 작업 하나가 판정 트랜잭션의 커넥션을 하나 쓰고, 기다리는 동안에는 쥐지 않는다.
- 메모리는 작업 수 상한(4096)으로 묶인다. 완료 콜백 목록이나 future를 쌓지 않는다.

### 3.3 비교와 정리 규칙

- 비교 기준은 수신 때 한 번 정한 순서 시각(`min(ts_ms, 수신 시각)`)이고, 처리 때도 같은 값을 쓴다(LLD-0140). 잰 시각이 없는 구형 위치는 도착 순서로 비교한다.
- 들어온 위치가 최신 대기(없으면 실행 중)보다 늦게 잰 것이면 최신 대기가 된다. 같거나 먼저 잰 것이면 밀린 항목이 된다(같은 위치 재전송 포함).
- **밀린 항목은 같거나 늦게 잰 작업이 끝난 결과로 답한다.**
  - 그 작업이 `APPLIED`이거나 `SKIPPED`이면 `SKIPPED`다(요청 좌표, `locationSource=REQUEST`). 더 최근 위치가 실제로 반영됐거나, 밀린 항목도 이미 최신보다 먼저 잰 것이다.
  - 그 작업이 `REJECTED`이면 `REJECTED`다. 같은 회원이라 거절 이유(시니어 아님)도 같다.
  - 그 작업이 실패하면 밀린 항목은 다음 작업을 기다린다. 회원에게 더 처리할 작업이 없으면 과부하로 끝낸다(ACK 없음, 재전송).
- 큐에 넣었다는 이유만으로 성공 ACK를 보내지 않는다. 기술 오류, 과부하를 `REJECTED`로 바꾸지 않는다.
- 판정 결과는 예전과 같다. 같은 회원 몰림에서 중간 위치를 실시간에 반영하지 않는 것(LLD-0140 밀어내기)도 그대로다. 우편함은 이를 수신 스레드 밖에서 할 뿐이다.

### 3.4 응답 경로와 경계

| 경우 | 응답 | 보내는 곳 |
| --- | --- | --- |
| v2 입력 오류, 본인 아님 | `REJECTED` | 수신 스레드, `@SendToUser` |
| 구형 입력 오류 | 예외 → `/user/queue/errors` | 수신 스레드(예전과 같음) |
| 실행 결과 | `APPLIED`, `SKIPPED`, `REJECTED` | 실행기 스레드, `WebSocketWorkDispatcher.sendToSession` |
| 실행 중 기술 오류 | ACK 없음, 오류를 `/user/queue/errors` | 실행기 스레드, `sendError`(LLD-0091과 같은 로그 형식) |
| 과부하(자리 없음, 밀린 항목 축출, 대신할 작업 없음, 종료 중 거절) | ACK 없음, `TEMPORARILY_BUSY` | `sendOverloaded` |

- 발신 세션, 인증 정보(Principal), MDC는 수신 스레드에서 작업에 담아 넘긴다. 작업 스레드는 그 세션에만 보낸다(LLD-0088). 과부하 응답은 수신 스레드에서 불릴 수 있어 끝나면 그 스레드의 원래 MDC로 되돌린다.
- 연결이 끊긴 세션: 처리는 끝까지 하고(최신 위치는 반영한다), 그 세션으로 보낸 응답은 브로커가 버린다.
- 서버 종료: 실행기는 실행 중과 대기열의 작업을 끝내도록 최대 10초 기다린다. 그 뒤 차례 등록이 거절되면 남은 작업을 과부하로 끝내고 회원 항목을 지운다.
- 회원 상자는 실행, 대기, 밀린 항목이 모두 비면 지운다. 지우는 중인 상자를 받은 제출자는 닫힘 표시를 보고 새 상자로 다시 시도한다.
- 동기 경로(`receive`, `applyRealtime`)는 회원 순서 잠금을 그대로 쓴다. STOMP 경로는 우편함이 회원 실행을 하나로 줄여 그 잠금에서 기다리지 않는다. 같은 회원을 두 경로가 함께 처리해도 순서 잠금이 최신 비교부터 최신 위치 저장까지를 하나씩 실행한다.

### 3.5 고려한 대안

| 대안 | 기각 이유 |
| --- | --- |
| 수신 풀 크기만 늘리기 | 한 회원이 늘린 만큼 또 차지한다 |
| 기존 동기 잠금 호출을 공용 실행기로 옮기기 | 그 실행기를 한 회원이 차지한다(공정성 없음) |
| 최신 위치도 대기 상한으로 엄격히 거절 | 구현은 단순하지만 최신 위치가 빠지고 앱 재전송에 기대야 한다. 앱 위치 ACK 재전송은 아직 없다 |
| 회원별 무제한 대기열 | 메모리 상한이 없다 |

대가: 응답이 수신 스레드 반환 뒤에 따로 간다. 실행기 대기 시간만큼 ACK가 늦어질 수 있고, 몰린 회원의 밀린 항목 중 상한을 넘은 것은 ACK 대신 과부하 오류를 받는다.

## 5. 설정

`websocket.executor.location.threads`(8), `location.ingest.max-waiting-per-member`(16), `location.ingest.max-members`(1024), `location.ingest.max-queued`(4096). 지표: `executor.*{name=websocket.location}`, `location.ingest.members`, `location.ingest.queued`.

## 6. 인수조건

- [ ] 수정 전에는 회원 A의 몰림으로 공용 수신 스레드가 막혀 결정적 회귀 테스트가 실패하고, 수정 뒤에는 A의 지연을 풀기 전에 B의 처리가 끝난다(`LocationMemberIsolationStompTest`)
- [ ] 회원별 실행, 대기, 밀린 항목과 전체 회원, 작업 수에 상한이 있고 과부하 때 수신 스레드가 작업을 대신 실행하지 않는다(`MemberLocationMailboxTest`)
- [ ] 최신 위치가 옛 위치로 되돌아가지 않는다(STOMP 테스트에서 A의 최종 최신 위치 = 가장 늦게 잰 위치, 우편함 동시성 테스트)
- [ ] 더 최근 위치가 반영되기 전에는 밀린 위치를 성공으로 확인하지 않는다. 기술 실패나 대기열 진입만으로 성공 ACK를 보내지 않는다(`LocationIngestAsyncTest`, `MemberLocationMailboxTest`)
- [ ] `APPLIED`, `SKIPPED`, `REJECTED` 계약이 그대로이고 위치 원본 INSERT가 없다
- [ ] 같은 시각 재전송, 역순, 구형, 권한 위반, 실패 후 재시도, 발신 세션 격리, 종료 뒤 회원 항목 정리를 검증한다
- [ ] 로컬 k6 혼합 트래픽 전후 비교(8절)
- [ ] `bash scripts/harness/verify.sh`, 코드 검수

## 7. 미결정 사항

- 상한 기본값(밀린 항목 16, 회원 1024, 작업 4096, 스레드 8)은 로컬 측정 기준이다. 운영 트래픽 기준 조정은 운영 구축 뒤 한다.
