## 1. 목적 / 배경

집에 머무는 어르신의 GPS가 안심구역(반경 75m) 밖으로 한 번 찍히면 서버가 그 위치 하나로 이탈을 판정해 보호자에게 「벗어났어요」(Z01)를 보내고, 다음 위치가 안으로 들어오면 「돌아왔어요」(Z02)를 보낸다. 개발 서버에서 회원 28은 2026-11-27 21:11:53 이탈, 21:12:06 돌아옴(13초), 회원 37은 11-28 12:17:31 이탈, 12:17:33 돌아옴이 갔다.

LLD-0190은 돌아온 뒤 30분 묶음 안의 흔들림만 막는다. 귀가 30분 뒤 집에 머무는 동안의 튐은 묶음이 끝난 상태라 그대로 가짜 이탈, 돌아옴 쌍이 된다. 위치는 대략 5~30초 간격으로 오므로, 밖으로 찍힌 상태가 일정 시간 이어질 때만 이탈로 본다.

## 2. 범위

### In scope
- 변경 모듈: widyu-domain(`SeniorStayState`), widyu-api(`LocationJudgeService`, `application.yml`, Flyway `V9`)
- 안 → 밖 전이의 확정 지연. 설정 `location.safe-zone.exit-confirm-sec`(기본 60초, 0이면 지금처럼 즉시)

### Out of scope
- 밖 → 안(돌아옴)은 지연하지 않는다. 확정 시간 안의 튐은 이탈이 확정되지 않아 돌아옴도 생기지 않는다
- 30분 묶음 규칙(LLD-0190, 5.2)과 Z01, Z02 문구, 수신자는 그대로다
- 안심구역 반경(75m), 같은 자리 반경(30m), 정확도(`accuracy_m`)를 쓰는 필터는 바꾸지 않는다
- 체류 지점이 안심구역 경계 근처일 때 그 30m 안의 밖 위치는 지금도 같은 자리로 보아 판정을 타지 않는다. 확정 대기가 없을 때의 이 동작은 그대로다
- 확정 대기 중에 위치가 끊긴 경우를 서버가 따로 확정하지 않는다(스케줄러 없음). 다음 위치가 올 때 확정한다

## 3. 인터페이스 / API

API 변경 없음. 위치 ACK, 방송, 조회 응답의 형식은 그대로다. 확정 대기 중 응답의 `locationType`, `locationName`, `stayStartTime`은 안심구역 안 체류 값이고 좌표는 받은 위치다.

설정:

```yaml
location:
  safe-zone:
    exit-confirm-sec: ${LOCATION_SAFE_ZONE_EXIT_CONFIRM_SEC:60}
```

## 4. 데이터 모델

`senior_stay_state`에 칸 하나를 더한다. 엔티티는 widyu-domain `SeniorStayState.pendingExitSince`.

| 칸 | 타입 | 뜻 |
| --- | --- | --- |
| `pending_exit_since` | `DATETIME(6) NULL` | 안심구역 안 상태에서 밖으로 처음 찍힌 시각. 값이 있으면 이탈 확정 대기 중이다. 확정하거나 다시 안으로 찍히면 지운다 |

마이그레이션: `backend/widyu-api/src/main/resources/db/migration/V9__senior_stay_state_pending_exit.sql`(NULL 허용 칸 추가만). 기존 행은 NULL(대기 아님)이다. `LegacyStayStateImporter`가 옮겨 오는 행과 첫 위치로 만드는 행(`start`)도 NULL로 시작한다. 예전 Redis 상태에는 대기 개념이 없어 옮길 값이 없다.

## 5. 처리 흐름

위치 한 건의 판정(`LocationJudgeService.decideStay`, 위치 처리 트랜잭션 안). 잠금 규칙은 LLD-0141 5.1, 5.3 그대로다.

1. 잠그지 않고 읽는다. 체류 지점 30m 안이고 **확정 대기가 없으면** 그대로 응답하고 끝(쓰기, 잠금 없음)
2. 아니면 행을 `PESSIMISTIC_WRITE`로 잠가 다시 읽고 1과 같은 조건이면 끝. 행이 없으면 잠그지 않고 INSERT(지금과 같다)
3. 안심구역 매칭(75m)
4. 이전 상태가 구역 안(HOME, OTHER)이고 새 위치가 모든 구역 밖이면:
   - 대기가 없으면 `pending_exit_since = 지금`을 쓰고, 상태와 알림은 그대로 둔 채 끝
   - 대기 중이고 `지금 < pending_exit_since + 확정 시간`이면 아무것도 쓰지 않고 끝
   - 지났으면 5로 간다(이탈 확정)
5. 구역 안 위치이고 체류 지점 30m 안이면(대기 중에 다시 안으로 찍힘) 대기만 지우고 끝. 알림 없음
6. 그 밖이면 지금처럼 `moveTo`(대기도 지운다) + `applySafeZoneTransition`. 이탈 확정이면 이 단계에서 30분 묶음 규칙으로 Z01 여부를 정한다

### 5.1 판단 근거

- **확정 대기 중에는 같은 자리 지름길을 건너뛴다(1, 2단계).** 지름길은 판정을 아예 하지 않으므로, 대기 중 위치가 체류 지점 30m 안에 오면 확정 검사가 영원히 돌지 않을 수 있다. 예: 경계 근처 집 체류 지점에서 55m 밖으로 찍혀 대기가 시작된 뒤, 체류 지점 22m 안이면서 구역 밖인 자리에 서 있는 경우. 그래서 지름길 조건에 「대기가 없음」을 더했다. 대기 중에는 위치마다 행을 잠그지만 대기는 최대 확정 시간만큼이고, 값이 바뀌지 않으면 UPDATE는 나가지 않는다.
- **확정 대기 중에는 체류 지점(좌표, `stay_started_at`)을 옮기지 않는다.** 확정 전에는 구역 안에 있다고 보는 원칙이라, 튄 위치로 체류 지점을 옮기면 돌아왔을 때 체류 시작 시각이 바뀌고 외출 여부 조회가 흔들린다. 체류 지점이 집에 남아 있으므로 위 지름길 문제는 대부분 생기지 않지만, 경계 근처 체류 지점의 경우를 위해 1단계 조건을 함께 둔다.
- **대기 중 구역 안 다른 자리(30m 넘게 떨어짐)로 찍히면 6단계 `moveTo`로 옮긴다.** 구역 안 → 안 이동이라 알림은 없고, 대기는 `moveTo`가 지운다.
- **확정 시각은 확정한 지금 시각이다.** `moveTo`의 `stay_started_at`과 묶음 끝(`alert_until = 지금 + 30분`) 모두 확정 시점 기준이다. 밖 체류 지점은 확정한 위치이므로 그 자리에 온 시각을 쓴다. 처음 밖으로 찍힌 시각을 쓰면 그 위치와 다른 좌표의 시작 시각이 되고, 묶음 끝이 실제 Z01 발송보다 앞당겨진다.
- **확정 시간 0은 지금 동작과 같다.** `holdExit`가 대기 시각을 남겼다가 바로 확정하고 `moveTo`가 지우므로, 같은 트랜잭션 안에서 칸은 NULL로 돌아온다.

### 5.2 상태별 동작

| 이전 | 새 위치 | 대기 | 결과 |
| --- | --- | --- | --- |
| 구역 안 | 구역 밖 | 없음 | 대기 시작. 상태, 알림 그대로 |
| 구역 안 | 구역 밖 | 확정 시간 전 | 그대로 |
| 구역 안 | 구역 밖 | 확정 시간 지남 | 이탈 확정. 기존 규칙으로 Z01 |
| 구역 안 | 구역 안, 체류 지점 30m 안 | 있음 | 대기만 지움. 알림 없음 |
| 구역 안 | 구역 안, 30m 넘게 | 있음/없음 | `moveTo`(안 → 안), 대기 지움, 알림 없음 |
| 구역 밖 | 구역 안 | - | 지금 규칙(LLD-0190). 지연 없음 |

## 6. 예외 / 에러 처리

새 오류 코드 없음. 대기 시각 쓰기는 판정 트랜잭션 안에서 상태, Outbox와 함께 커밋, 롤백된다. 롤백되면 다음 위치에서 대기를 다시 시작한다(확정이 그만큼 늦어질 수 있다).

### 6.1 알고 받아들인 한계: Redis 최신 위치 쓰기 실패 뒤의 순서

판정 트랜잭션이 커밋된 뒤 Redis 최신 위치 쓰기가 실패하면 ACK가 가지 않아 같은 위치가 재전송되고, Redis에는 그 이전 위치가 남아 늦게 도착한 옛 위치도 다시 판정된다. 확정 시간을 서버 시각으로 재므로 다음이 생길 수 있다.

- 대기를 연 밖 위치가 확정 시간 넘게 뒤에 재전송되면 새 측정 없이 이탈을 확정한다(Z01)
- 대기를 지운 안 위치의 Redis 쓰기가 실패한 뒤 그보다 먼저 잰 밖 위치가 늦게 오면 대기를 다시 열고, 실제로는 안에 있던 시간까지 확정 시간으로 셀 수 있다
- 같은 자리(30m) 위치는 행을 쓰지 않으므로 그 시각에 구역 안이었다는 사실이 남지 않는다

이는 이 기능이 만든 문제가 아니라, 순서 판정이 커밋된 상태가 아닌 Redis 최신 위치에 기대는 기존 구멍(LLD-0140)이 시간 조건을 가진 판정에서 드러난 것이다. 최악의 결과는 확정 지연이 없던 이전 동작(즉시 이탈 알림)과 같다. 측정 시각 기준, 행에 기준 시각을 남기는 방법을 시험했지만 기기 시계 오류, 15분 경계, 옛 형식(`timestamp`만 있음), 같은 자리 지름길마다 새 틈이 생겨 이 PR에서 닫지 않는다. #1181에서 다룬다(사용자 결정, 2026-11-28).

## 7. 인수조건 (Acceptance Criteria)

- [ ] 구역 안 상태에서 밖으로 한 번 찍히고 확정 시간 안에 다시 안으로 찍히면 Z01, Z02가 0건이고, `locationType`과 `stay_started_at`, 체류 좌표가 그대로이며 `pending_exit_since`가 NULL이다
- [ ] 밖으로 찍힌 뒤 확정 시간이 지나도록 계속 밖이면 그다음 밖 위치에서 이탈로 확정하고 Z01이 1건이며 `pending_exit_since`가 NULL이다
- [ ] 확정 대기 중 체류 지점 30m 안이면서 구역 밖인 위치가 와도 확정 시간이 지났으면 이탈로 확정한다
- [ ] 확정 대기 중 체류 지점 30m 안의 구역 안 위치가 오면 대기만 지우고 체류 지점을 옮기지 않는다
- [ ] 확정 시간이 0이면 밖으로 찍힌 첫 위치에서 Z01을 발행한다
- [ ] 돌아옴 뒤 30분 묶음 안에서 확정된 재이탈과 재진입은 Z01, Z02를 더 만들지 않고, 묶음이 끝난 뒤의 짧은 튐도 알림이 없다
- [ ] 대기 시각이 실제 DB 행에 커밋되고, 다음 위치 트랜잭션에서 읽혀 확정과 취소가 동작한다(`StayStateOutboxAtomicityTest`)
- [ ] 빈 MySQL에 V1~V9를 적용하면 엔티티 스키마 검증을 통과한다(`FlywayMigrationMySqlTest`)
- [ ] `./gradlew :backend:widyu-api:test`가 통과한다

## 8. 영향 범위 / 마이그레이션

- **감수점: 실제 이탈 알림이 최대 확정 시간(기본 60초)에 위치 간격을 더한 만큼 늦어진다.** 서버는 위치가 올 때만 확정하므로, 60초가 지난 뒤 첫 밖 위치에서 Z01이 나간다. 위치가 30초 간격이면 최대 약 90초다. 확정 시간보다 긴 튐(60초 넘게 밖으로 찍힘)은 여전히 가짜 알림이 된다.
- 확정 대기 중 보호자 화면의 외출 여부(`getOutingStatus`)와 체류 시간은 구역 안 값이다. 좌표 방송은 받은 위치 그대로다.
- 배포: V9가 칸을 더한 뒤 새 코드가 뜬다. 기존 행은 NULL이라 배포 직후 동작은 「대기 없음」에서 시작한다. 배포 시점에 밖으로 막 찍힌 어르신은 다음 밖 위치부터 확정을 센다.
- 롤백: 이전 코드는 이 칸을 모르지만 NULL 허용이라 그대로 뜬다(dev, prod `validate`는 엔티티에 없는 칸을 검사하지 않는다).
- Flyway 번호: V6, V7은 열린 PR #1160, #1162, V8은 병렬 PR #1180(이슈 #1178)이 쓴다. 이 PR이 V9를 먼저 머지하면 그보다 낮은 번호의 새 파일은 Flyway가 거부하므로(LLD-0154 「병렬 PR의 버전 번호」) 나중 PR이 번호를 올린다.
- MySQL ENUM 변경 없음.

## 9. 미결정 사항 (Open Questions)

- [ ] 기본 확정 시간 60초가 맞는가. 근거: 개발 서버의 튐은 2~13초였고, 60초면 위치 2~12번을 밖으로 더 받아야 확정된다. 늦어짐은 1분 남짓이다. 더 길면 튐을 더 막지만 실제 이탈 알림이 늦어진다(정책 확인 필요, 이슈 #1179)
